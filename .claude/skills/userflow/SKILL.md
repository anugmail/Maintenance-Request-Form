## 1. userflow คืออะไร

บอร์ด FigJam ที่ทีมเจ้าของงานวาดหลังรอบ refinement — **1 scenario = 1 เส้นทางที่ผู้ใช้หนึ่งบทบาทเดินบนหน้าจอเพื่อทำงานหนึ่งอย่างให้จบ**
ข้างเส้น flow มี wireframe หยาบของแต่ละหน้า และโน้ตเงื่อนไขรายหน้า · เจ้าของงานส่งมาเป็น**ข้อความที่ก๊อปจากบอร์ด** ไม่ใช่ภาพ

อยู่ตรงไหนของชุดเอกสาร (`Diagram/<เรื่อง>/`):

| ชั้น | ไฟล์ตัวอย่าง (Overhaul) | ตอบคำถาม |
|---|---|---|
| ผังกระบวนการ | `08-overhaul-กระบวนการใหม่.md` | งานเดินยังไงทั้งองค์กร |
| Journey | `09-overhaul-journey-กบค.md/.csv` | บทบาทหลักทำอะไรตั้งแต่ต้นจนจบ |
| Scenario (กิจกรรม) | `10-overhaul-scenario.csv` (OH-01…) | ทำอะไรได้บ้าง |
| Use case | `11-overhaul-usecase.csv` | บนจอทำอะไรได้ |
| **Userflow** | บอร์ด FigJam (Scenario 1–14) | **กดอะไร เห็นหน้าไหน มีเงื่อนไขอะไร** |
| สถานะ | `12-overhaul-สถานะ.md/.csv` | ข้อมูลอยู่สถานะไหน เปลี่ยนเมื่อไร |

⚠️ คำว่า **scenario ซ้อนกันสองความหมาย** — ใน 10-…csv คือ*กิจกรรม* (OH-xx) · บนบอร์ด userflow คือ*เส้นทางบนจอ* (Scenario N) เลขไม่ตรงกัน ห้ามจับคู่ด้วยเลข

## 2. อ่านข้อความจากบอร์ดยังไง

ข้อความที่ก๊อปมา**เรียงตามลำดับชั้นบนบอร์ด ไม่ใช่ลำดับการอ่าน** ⇒ ข้อความของหลาย scenario ปนกัน และหน้าเดียวกันซ้ำหลายรอบ (ใช้หลาย scenario) ต้องประกอบใหม่เอง

**สัญลักษณ์ 4 แบบ (หัวบอร์ดเขียนไว้เสมอ):** `start/End` จุดเริ่ม/จบ · `Display` หน้าจอ · `Action` สิ่งที่ผู้ใช้ทำ · `Dicision/Condition` ทางแยก (ลงท้าย `?` ตามด้วย `Y`/`N`)

**ก้อนที่เจอบนบอร์ด**

| ข้อความ | แปลว่า |
|---|---|
| `Scenario N` + `กบค. สร้างแผน Overhaul` | หัว scenario = บทบาท + งาน |
| `refinement scenario …` + ชื่อคน | ป้ายว่า scenario นี้ refine กับใครแล้ว (ไม่ใช่เนื้อหา) |
| `Permission` · `กบค view และ edit` · `หน่วยงาน view` | สิทธิ์ตามบทบาท |
| `to do` · `assign` · `status` · `เล่า journey` · `เฟรม` | งานค้างของทีมเจ้าของงาน — ไม่ใช่ UI |
| `start` → `กดเมนู` → `หน้า X` → `ระบุข้อมูล` → `ระบุครบ ?` Y/N → `บันทึก` | เส้น flow · ทางแยกที่เจอบ่อย: `ระบุครบ ?` `ต้องการออก` `บันทึก ?` `ต้องการแก้ไข ?` `ต้องการลบ ?` `มีแผน ?` `มีผลการตอบกลับ ?` |
| `<ชื่อหน้า> - Condition` / `- Condition` ใต้ชื่อหน้า | **โน้ตเงื่อนไขรายหน้า — ของที่ต้องทำตามตัวอักษร** |
| `มาจาก 2 ทาง` · `ทางหน้า list` · `หน้ารายละเอียด` | จุดเข้าหน้านี้มีกี่ทาง ต้องทำครบทุกทาง |
| ป้ายช่อง + ค่าตัวอย่าง `xxx` `2569` `1,000.000` `Filename.pdf` `WBS1234` | wireframe — เอาชื่อช่อง/คอลัมน์ ค่าตัวอย่างเป็นแค่รูปแบบ |
| `. . .` ในแถว | เมนู "…" ท้ายแถว (`Action list` บอกรายการในเมนู) |
| `Select   V` · `[  ]` · `detail / ทะเบียน เลขไมล์ อายุการใช้งาน` | dropdown · checkbox · แถวรายการรถ |
| ชื่อขั้นซ้ำเป็นชุด (`นัดเอารถเข้าอู่ ตรวจรับรถ … ปิดงาน`) | stepper ของหน้านั้น |
| `จอง section เฉยๆ` | เว้นที่ไว้ ยังไม่มีเนื้อหา — ทำเป็นส่วนว่าง/เร็วๆ นี้ อย่าคิดเนื้อหาเอง |
| `(ยังไม่รู้)` · `(ตามของเดิม)` · `(mockup)` | ยังไม่เคาะ / ใช้ค่าระบบเดิม / ข้อมูลจำลองได้ |

**ศัพท์ในโน้ตเงื่อนไข → ของที่ทำ**

| ในโน้ต | ทำเป็น |
|---|---|
| `Freetext` · `Text number` | Text input (ตัวเลขจัดรูปแบบหลักพัน) |
| `dropdown select` · `Select` | Input dropdown |
| `search select` | dropdown พิมพ์ค้นได้ (`.combo`) |
| `Display` · `ดึงข้อมูล display` | ช่องอ่านอย่างเดียว เติมจากระบบ |
| `multi select` + เพิ่ม/ลบรถจากรายการที่เลือก | dual list (`.dual`) |
| `date range ไม่สามารถเลือกน้อยกว่า todays` | ช่วงวันที่ min = วันนี้ |
| `default …` · `ไม่มีปีย้อนหลัง` | ค่าตั้งต้น · ขอบเขตตัวเลือก |
| upload: `จำนวนสูงสุด 10 file` `pdf,jpeg` `download ได้` `preview ได้` | กล่องอัปโหลด + รายการไฟล์ (`.fu`) |
| `ปุ่มย้อนกลับ มีการแก้ไข มี confirm modal / ไม่มีการแก้ไข ไม่มี CF modal` | เช็คฟอร์มสกปรกก่อนออก |
| `ปุ่มบันทึก มีการแก้ไข มี cf change` | modal ยืนยันการแก้ไข เฉพาะเมื่อแก้จริง |
| `toast สำเร็จ คำว่า "…"` | Notification **ข้อความตรงตัวอักษร** (รวมตัวพิมพ์เล็ก/ใหญ่) |
| `ถ้ายังไม่มี… จะ Disable ปุ่ม` · `มีมากกว่า 1 รายการจะลบได้` | เงื่อนไขปิดปุ่ม/ซ่อนการลบ |

## 3. ได้ userflow มา → ออกแบบหน้าจอ (ลำดับที่ทำจริงกับ Overhaul)

ถามก่อนลงมือทุกจุดที่เป็นการตัดสินใจ (กติกาเจ้าของงาน: อ่านให้ครบ → ถาม → ค่อยสร้าง) · คำถามเรื่องกระบวนการถามเป็นข้อความ ไม่ยัดเป็นตัวเลือก

0. **เก็บข้อความดิบนอกรีโป** (`~/PEA/Maintain-D/userflow/`) · ถามขอบเขต: ใช้แทนของเดิมไหม ("แทนแผนเดิม") · ทำทุก scenario หรือบางช่วง
1. **ประกอบใหม่เป็นตาราง scenario × หน้าจอ** — แต่ละ scenario: บทบาท · จุดเข้า · หน้าที่ผ่าน · ทางแยก Y/N · เงื่อนไขของหน้า · แยกให้ชัดว่าข้อไหน*บอร์ดเขียน* ข้อไหน*ตีความเอง* (ตีความ = ติดป้าย "รอเคาะ")
2. **ตารางสถานะ + sequence diagram** → `Diagram/<เรื่อง>/NN-<เรื่อง>-สถานะ.md` + `.csv` (ตัวอย่าง `12-overhaul-สถานะ.md`: ตารางสถานะ · เทียบของเดิม · sequence · "ยังไม่รู้ ต้องถามต่อ") · mermaid ต้อง parse ผ่านจริง
3. **จับคู่ส่วนของหน้า → component จริง** → `figma-export/<เรื่อง>-component-map.md` · ทุกชิ้นต้องชี้กลับไลบรารี (Component) VMS Plus + หน้า UI Release#2 ได้ (`node design-system/figma-screens.js …`) · ไม่มีในไลบรารี → หยุดถาม · ข้อมูลที่ API ให้ไม่ได้ → ไม่ใส่ใน UI
4. **mock HTML** → `design-mock/<เรื่อง>-v2-0N-*.html` + `<เรื่อง>-v2-mock.js` (localStorage) · ทำเงื่อนไขในข้อ 2 ครบทุกข้อ · Tailwind + คลาส design-system ไม่มี `style=` · กติกา mobile (< 768: ตาราง→การ์ด · popup→bottom sheet) · ปุ่มท้ายหน้า: ย้อนกลับ/ยกเลิกซ้าย ยืนยันขวา ปุ่มเดียวชิดขวา · อัปโหลด 1 คอลัมน์ · แถว WBS ตามข้อ F10 ใน `plan.md` · ไล่กดด้วย Playwright ตาม skill `verify` · ลงการ์ดใน `design-mock/index.html`
5. **Figma** → **อ่าน `figma-export/component-rules.md` ก่อน (กติการายจุด · เทสต์บังคับผ่าน `component-rules.json`)** · **เรื่องใหม่ = ปลั๊กอินใหม่** (เจ้าของงานสั่ง 20 ต.ค. 2569 "แยกออกเป็นสองเรื่อง"): โฟลเดอร์ `figma-export/<เรื่อง>-plugin/` เขียนแค่ `screens.js` แล้ว `node figma-export/build-plugin.js <โฟลเดอร์>` ประกอบกับ `plugin-lib/core.js` เป็น `code.js` · หน้า Figma + คำนำหน้าเฟรมของตัวเอง · เทสด้วย harness เดิมผ่าน env (ดู `figma-export/README.md`) · **ยืมของที่ออกแบบไว้ใน flow อื่นของไฟล์ Maintain-D ได้** (สำรวจดัมป์ `out/figma-dump/maintain-d/` ก่อน ใส่ชื่อใน `LOCAL_OPTIONAL` · ตัวอย่าง `maintainance-plugin/`) · แบบเดิม `figma-export/overhaul2-plugin/` (`createInstance` จากไลบรารี "component" ⇒ Go to main component พาไปไฟล์ที่อ่านค่า) · **1 จอ = 1 เฟรมพื้นขาว ไม่ใช้ section · จัดวางแบบตาราง flow ของทีมออกแบบ (R19 · 20 ต.ค. 2569): 1 scenario = 1 บล็อกตัวอักษร → ป้าย A.1 A.2 = state → แถว Desktop 1440 → แถว Mobile 402×874 ใต้คอลัมน์เดียวกัน · สร้างบนหน้าใหม่ทุกครั้ง ไม่แตะชุดเดิม + ป้าย Device/Desktop/Mobile ซ้าย (`buildGrid()` ใน plugin-lib/core.js · GROUPS ต่อปลั๊กอิน)** · แก้ทีหลังทำเป็นปุ่ม "แก้เฉพาะจุด" (ย้าย instance เดิม ไม่สร้างใหม่ · กดซ้ำได้) · ทดสอบด้วย harness `figma-export/test-overhaul2-plugin.js` ก่อนให้รัน (Figma รับ `layoutGrow` แค่ 0/1)
6. **FigJam** → capture ไล่กดจริง (`flow-<เรื่อง>-capture.js`) → `3-figjam-board.js --<เรื่อง> --only --out=board-<เรื่อง>.json` → ปลั๊กอิน figjam (วางต่อใต้ของเดิมได้)
7. **AC** → ระดับ scenario `Diagram/<เรื่อง>/NN-<เรื่อง>-AC.md` (กติกาหัวไฟล์ 15) + ระดับหน้า `NN-<เรื่อง>-AC-หน้าN-<ชื่อหน้า>.md` (ฟิลด์ · ต้องแสดงอะไร อย่างไร · แสดงเมื่อ · ค่าเมื่อไม่มีข้อมูล · ไม่อ้างแหล่งที่มา · แม่แบบไฟล์ 18) → ลง FigJam บอร์ดเดียวกับ userflow ด้วย `figma-export/9-ac-board.js --src=… --out=board-ac-<เรื่อง>.json --prefix=…` → ปลั๊กอิน figjam (section ชนิด doc: กล่องข้อความ + ตาราง)
7. commit + push เมื่อเจ้าของงานยืนยัน → อัปเดต `plan.md` (เฉพาะเครื่อง local ไม่ commit) · flow เปลี่ยน → แก้ผังใน `Diagram/` คอมมิตเดียวกัน

## 4. ถูกสั่งให้ "ออกแบบ userflow" เรื่องใหม่

เขียนในภาษาเดียวกับบอร์ด เพื่อให้ทีมเจ้าของงานอ่านต่อ/วางบนบอร์ดได้ทันที

1. **ถามก่อน:** บทบาทที่เดิน · เรื่องเริ่ม-จบตรงไหน · ใช้ journey/scenario/use case ชุดไหนเป็นฐาน (ถ้ามีใน `Diagram/`) · ทำแทนของเดิมหรือเพิ่ม
2. **เสนอรายการ scenario ให้เคาะก่อนวาด** — ชื่อแบบบอร์ด `<บทบาท> <ทำอะไร>` 1 งาน 1 scenario · สร้าง/แก้ไข/ลบ แยก scenario · ทางแยกที่ไม่ได้เกิดทุกครั้ง (ปฏิเสธนัด ฯลฯ) เป็นทางแยกในเส้น ไม่ใช่ scenario ใหม่ เว้นแต่เจ้าของงานสั่ง
3. **ต่อ scenario เขียน 3 ส่วน**
   - **flow** ด้วยสัญลักษณ์ 4 แบบ: start → `กดเมนู` → Display → Action → Decision `?` (Y/N ครบทุกทาง ทุกทางต้องไปจบ) → End · ระบุ `มาจาก N ทาง` เมื่อเข้าได้หลายหน้า
   - **wireframe** ของทุก Display: ชื่อหน้า · section · ชื่อช่อง/คอลัมน์ + ค่าตัวอย่าง · ปุ่ม Action
   - **Condition** ของทุกหน้าที่มีช่องกรอก ใช้ศัพท์ในตารางหัวข้อ 2 (ชนิดช่อง · default · ขอบเขต · upload · ปุ่มย้อนกลับ/บันทึก · toast ข้อความจริง · เงื่อนไขปิดปุ่ม) — ข้อที่ยังไม่รู้เขียน `(ยังไม่รู้)` ไม่เดา
   - ใส่ **Permission** รายบทบาท
4. **ส่งมอบ**: `Diagram/<เรื่อง>/NN-<เรื่อง>-userflow.md` (หัวข้อ `### Scenario N · <บทบาท> <ทำอะไร>` + mermaid ต่อ scenario — `([ ])` start/End · `[ ]` Display · `( )` Action · `{ }` Decision · `%% Q: <node> | คำถาม` = sticky — + wireframe + ตาราง Condition + Permission · ตัวอย่างจริง `Diagram/01-บำรุงรักษาตามวาระ/14-บำรุงรักษา-userflow.md`) · ลงบอร์ด FigJam ด้วย `figma-export/8-flow-userflow.js --src=… --out=…` → `3-figjam-board.js --<ธง> --only --out=board-<เรื่อง>.json` (รูปทรง Template · section ละ scenario · ไม่ต้องมีหน้าจอก่อน) · เทส `SPEC=board-<เรื่อง>.json node figma-export/test-figjam-plugin.js` + `Diagram/check-mermaid.js` ต้องผ่าน · แล้วทำต่อตามหัวข้อ 3 ข้อ 2 (ตารางสถานะ) เมื่อเจ้าของงานเคาะ
5. **ตรวจความสอดคล้อง**: ทุก use case ใน 11-…csv ต้องมีที่อยู่ในบาง scenario · ทุกทางแยกจบ · ชื่อสถานะตรงกับไฟล์สถานะ
