# Spec — เฟส 2 "ดำเนินการบำรุงรักษา" หน้าจริง

วันที่ 13 ส.ค. 2569 · สถานะ: ตกลงกับเจ้าของงานแล้ว รอทำแผน implement

## ปัญหา

โฟลว์บำรุงรักษาตามวาระทำเฟส 1 ครบแล้ว (ยืนยันรถ → เบิก/จัดหาอะไหล่ → แผนเดินทาง → ทวน + ยืนยัน)
แต่ **เฟส 2–5 ยังเป็นหน้าเปล่า** — กดเข้าไปเจอ `renderPlaceholder()` เท่านั้น

เฟส 2 คือคิวถัดไปที่ระบุไว้ใน `plan.md` แต่ติดที่ **เงื่อนไข 5 ข้อยังไม่เคาะ** (เก็บไว้ในจอ `ph2` ของ `plan-skeleton.html`) — 13 ส.ค. 2569 เจ้าของงานเคาะครบแล้ว รวมข้อที่โผล่มาระหว่างคุยอีก 3 ข้อ

## สิ่งที่จะได้

เฟส 2 ที่เดินได้จริงตั้งแต่ **แจ้ง กรย. เตรียมอะไหล่** → **บันทึกงานรายคัน** (รูปก่อน-หลัง · ของที่ใช้จริง · ตัวอย่างน้ำมัน) → **เอกสารส่งพัสดุ + แบบประเมิน** → **ปิดเฟส ปลดล็อกเฟส 3**
คันที่บำรุงรักษาไม่ได้ถูกบันทึกเหตุผลและติดธง "รอเลื่อนรอบหน้า" โดยไม่บล็อกคันอื่นและไม่บล็อกเฟส

## 3 · ลำดับใน flow

```
เฟส 2:  1. แจ้ง กรย. เตรียมอะไหล่ → 2. บันทึกงานรายคัน → 3. เอกสาร + แบบประเมิน → 4. ทวน + ปิดเฟส
```

- เข้าเฟส 2 ได้เมื่อ `plan.travelConfirmed === true` (กติกาเดิม ไม่แก้)
- ขั้นย่อยใช้กติกาเดียวกับเฟส 1 — **ถอยหลังได้เสมอ · เดินหน้าต้องผ่าน `validateMaintSub` ของทุกขั้นก่อนหน้า**
  (กันคลิก node บน stepper ข้ามขั้น — บั๊กที่เคยหลุดในเฟส 1)
- ปิดเฟส 2 → `plan.maint.confirmed = true` + `plan.phase = 'inspection'` ⇒ เฟส 3 ปลดล็อก

### ขั้น 1 · แจ้ง กรย. เตรียมอะไหล่

ที่มา: ผังเฟส 2 กล่อง `P → Q → N0` (กรย. เอาอะไหล่ไปวางจุดรวมงาน → VMS+ ออกเอกสาร → Noti ใกล้ถึงวัน)

- กบค. เห็นรายการ **ใบเดินทาง** ของแผน (จาก `plan.trips[]`) — แต่ละใบมี จุดรวมงาน (`trip.location`) · ช่วงวัน · จำนวนคัน · ยอดอะไหล่รวมของคันในใบนั้น
- กด **"ส่งแจ้ง กรย."** รายใบ (หรือส่งทุกใบพร้อมกัน) → สถานะใบ `pending` → `notified`
- กรย. เปิด `garage.html` เห็นใบที่ถูกแจ้ง → กด **"วางที่จุดรวมงานแล้ว"** (กรอกชื่อผู้ยืนยัน) → `ready`
- กบค. เห็นสถานะเด้งกลับในขั้นนี้ทันที
- **ผ่านขั้นนี้เมื่อทุกใบ = `ready`**

### ขั้น 2 · บันทึกงานรายคัน

- รายการรถ **จัดกลุ่มตามใบเดินทาง** (`.wgrp` + `.rzone` แบบเดียวกับขั้นยืนยันรถ) พร้อมสรุปต่อกลุ่ม
  รถที่ไม่ถูกใส่ไว้ในใบเดินทางใดเลย → กลุ่ม "ยังไม่อยู่ในใบเดินทาง" (อ่านอย่างเดียว บันทึกไม่ได้)
- คลิกแถวรถ → **drill-in เต็มหน้า** (แทนที่เนื้อขั้น พร้อมปุ่ม "← กลับรายการ") — ฟอร์มยาวเกินกว่าจะอยู่ใน modal หรือ inline
- ฟอร์มรายคัน 5 ส่วนตาม `skeleton-data.js` จอ `ph2`:

| ส่วน | ฟิลด์ | บังคับ |
|---|---|---|
| หัวงาน | เลขงาน · ทะเบียน · ยี่ห้อ/รุ่น · เขต (อ่านอย่างเดียว) · **ผู้ปฏิบัติงาน** · **วันที่เข้าทำงาน** | 2 ช่องท้าย |
| ก่อนทำ | รูป รถ+ทะเบียน · รูป อะไหล่ใหม่ · เลขไมล์ก่อน · ชม.เครื่องก่อน · สภาพที่พบ | รูป 2 + ตัวเลข 2 |
| รายการที่ทำจริง | ตาราง: ชื่ออะไหล่ · หมวด · จำนวนตามแผน · **จำนวนใช้จริง** · หน่วย · หมายเหตุ | จำนวนใช้จริงทุกแถว (0 ได้ ต้องใส่หมายเหตุ) |
| ตัวอย่างน้ำมันไฮดรอลิก | เก็บตัวอย่างไหม (บังคับ "เก็บ") · รหัสตัวอย่าง · ส่งแล็บวันที่ | ครบทั้ง 3 |
| หลังทำ | รูป รถ+ทะเบียน · รูป อะไหล่เก่า · รูป จุดซ่อม · เลขไมล์หลัง · ชม.เครื่องหลัง | รูป 3 + ตัวเลข 2 |

- เลขไมล์/ชม.เครื่อง **ก่อน** ตั้งต้นจาก master (`v.mileage` / `v.engineHours`) แก้ได้
- **หลังต้อง ≥ ก่อน** — ไม่งั้นเตือนแล้วปิดคันไม่ได้
- รายการอะไหล่ตั้งต้นจาก `MYD.deriveItems()` ของคันนั้น · จำนวนใช้จริง default = จำนวนตามแผน
- ปุ่ม **"บำรุงรักษาไม่ได้"** → สลับเป็นฟอร์มสั้น: เหตุผล · รูปประกอบ 1 · จะทำยังไงต่อ · เช็ก **"รอเลื่อนรอบหน้า"** (ติ๊กไว้ default)
  ⇒ `job.status = 'undone'` · ข้ามการตรวจรูป/ตัวเลขทั้งหมด
- ปิดคัน → `job.status = 'done'` | `'undone'` · กลับรายการ · แถวขึ้น badge
- **ผ่านขั้นนี้เมื่อรถทุกคันในใบเดินทางมี `status !== 'pending'`**

### ขั้น 3 · เอกสาร + แบบประเมิน

- การ์ด **ใบตรวจอะไหล่** และ **ใบตรวจสภาพงาน** — หัวข้อ + คำอธิบายหนึ่งบรรทัด + badge `ยังไม่เคาะรายละเอียด` · กดไม่ได้
- การ์ด **แบบประเมินความพึงพอใจ** — กบค. กด "ส่งแบบประเมิน" → ไปโผล่ที่ `confirm.html` ของ **หน่วยงานเจ้าของรถ** (หน่วยงานที่มีรถอยู่ในแผน) · กบค. เห็นตาราง ตอบแล้ว/ยังไม่ตอบ + คะแนนเฉลี่ย
- ปุ่มลิงก์ไป `supplies.html` ให้พัสดุกดรับทราบ (พัสดุ = ผู้รับทราบ ไม่ใช่ผู้อนุมัติ — ไม่บล็อก)
- **ผ่านขั้นนี้เมื่อกดส่งแบบประเมินแล้ว** — ไม่บังคับว่าต้องตอบกลับครบ (เจ้าของรถอาจตอบช้า ไม่ควรค้างเฟส)

### ขั้น 4 · ทวน + ปิดเฟส

- สรุป: ทำเสร็จ n คัน · ทำไม่ได้ m คัน (แยกรายชื่อ + ธงรอเลื่อน) · ใบเดินทาง k ใบ · แบบประเมินตอบกลับ x/y · เอกสารพัสดุรับทราบแล้ว/ยัง
- ปุ่ม **"ยืนยันปิดเฟส 2"** → `plan.maint.confirmed = true` · `plan.phase = 'inspection'` · บันทึก `statusHistory`
- หลังปิด — หน้าเฟส 2 กลายเป็นสรุปอ่านอย่างเดียว (ล้อ `renderProcurementConfirmed`) · `garage.html` และแบบประเมินใน `confirm.html` ล็อก

## 4 · โครงข้อมูล

`SCHEMA_VERSION` **8 → 9** — migration เติม `plan.maint` ให้แผนเดิมที่ยังไม่มี (ไม่ทำลายข้อมูลเก่า)

```js
plan.maint = {
  // ขั้น 1 — สถานะแจ้ง กรย. รายใบเดินทาง
  notify: {
    [tripId]: { status: 'pending'|'notified'|'ready', notifiedAt, by, at }
  },

  // ขั้น 2 — งานรายคัน
  jobs: {
    [vehicleId]: {
      status: 'pending'|'done'|'undone',
      worker, day,
      before: { photoVeh, photoPart, mileage, hours, found },
      used:   { [itemId]: { qty, note } },
      oil:    { taken: bool, code, sentAt },
      after:  { photoVeh, photoOld, photoSpot, mileage, hours },
      fail:   { reason, photo, next, deferNext: bool },
      at
    }
  },

  // ขั้น 3 — แบบประเมิน (ผู้ตอบ = หน่วยงานเจ้าของรถ)
  surveySentAt: null,
  survey: {
    [ownerDept]: { answers: { [questionId]: 1..5 }, by, at }
  },

  confirmed: false
}
```

**ช่องรูป** เก็บ `''` = ยังไม่แนบ · มีค่า = ชื่อไฟล์ mock (เหมือนฟอร์มแจ้งซ่อม) — ไม่เก็บ binary ใน localStorage

**คำถามแบบประเมิน** เพิ่มใน master (`MYD.SURVEY_QUESTIONS`) — ยกโครงจาก VMS Plus จริง
(`vms_mas_satisfaction_survey_questions`: `question_title` + `questions_description`) เรนเดอร์เป็นดาว 1–5 ต่อข้อ ส่งทีเดียวทั้งชุด

## 5 · logic ล้วน (ลง `mock-yearly.js` — เทสด้วย node)

| ฟังก์ชัน | คืนอะไร |
|---|---|
| `ensureMaint(plan)` | สร้าง `plan.maint` ถ้ายังไม่มี (migration-safe) |
| `notifyStatus(plan, tripId)` | `'pending'\|'notified'\|'ready'` |
| `notifyResolved(plan)` | ทุกใบ `ready` แล้วหรือยัง |
| `jobOf(plan, vehicleId)` | job object (สร้าง default ถ้ายังไม่มี) |
| `jobValid(plan, vehicleId, master)` | ฟอร์มครบพอปิดคันไหม (รูปครบ · ตัวเลขครบ · หลัง ≥ ก่อน · น้ำมันครบ · จำนวนใช้จริงครบทุกแถว) |
| `jobsResolved(plan, master)` | รถทุกคันในใบเดินทางมีข้อสรุปแล้วไหม |
| `maintSummary(plan, master)` | `{ done, undone, deferred, pending, total, trips }` |
| `surveyDepts(plan, master)` | รายชื่อหน่วยงานเจ้าของรถที่ต้องตอบ |
| `surveySummary(plan, master)` | `{ answered, total, avg }` |
| `maintLocked(plan)` | `plan.maint.confirmed === true` |

**กติกาที่ต้องมีเทสตรงๆ** (เคยพลาดแนวนี้มาแล้วในขั้นยืนยันรถ):
- คันที่ `undone` **ไม่ทำให้ `jobsResolved` เป็น false** และไม่ถูกนับเป็น "ยังไม่ทำ"
- `jobValid` ของคัน `undone` เช็กแค่ เหตุผล + รูป 1 ไม่เช็กรูปก่อน/หลัง
- `maintLocked` ล็อกทั้ง `garage.html` และแบบประเมิน ไม่ใช่แค่หน้า กบค.

## 9 · ส่งขึ้น FigJam

เจ้าของงานสั่ง 13 ส.ค. 2569: *"เขียนเสร็จอยากให้ทำ script ที่เขียนลง figjam ให้ด้วย"*
⇒ ทำ **ผัง + capture หน้าจอจริง** แบบเดียวกับโฟลว์ก่อนหน้า (สร้างแผน · วางแผนเดินทาง · แจ้งซ่อม)

**⚠️ ไปป์ไลน์นี้เขียนไว้แล้ว — รอบนี้คือ "ต่อของเดิม" ไม่ใช่สร้างใหม่**
ห้ามเขียนตัวแปลง mermaid / ตัว gen บอร์ด / ปลั๊กอินขึ้นมาซ้ำ ให้ใช้ของที่มีและแก้เท่าที่จำเป็น

**ข้อจำกัดที่กำหนดรูปงาน** — Figma REST API เขียน node ไม่ได้ · MCP แพลน Starter 20 call/เดือน (หมดแล้ว)
⇒ เขียนลง FigJam ได้ทางเดียวคือ **dev plugin** · script ที่ทำคือตัว generate `board.json` ให้ปลั๊กอินกิน
ขั้นกดสร้างบอร์ดใน Figma desktop ยังเป็นมือคน — **script ทำแทนไม่ได้ ไม่ต้องพยายาม**

| ไฟล์ | ของเดิมมีอะไรแล้ว | ต้องแตะแค่ไหน |
|---|---|---|
| `4-figjam-diagram.js` | แปลง mermaid → geometry (เลน · ชนิด node · เส้น · ป้าย) ครบแล้ว แต่ `SRC`/`OUT` เป็น const **ไม่มี argv เลย** | แก้ 2 บรรทัด → รับ `--src=<path.md> --out=<name.json>` · ไม่ใส่ = ค่าเดิม (regression ต้องผ่าน) |
| `3-figjam-board.js` | มี `flowSection()` เป็นตัวช่วยกลาง + ระบบแฟล็ก `--after/--pages/--all` อยู่แล้ว | เพิ่ม ~3 บรรทัด — แฟล็ก `--maint` เรียก `flowSection()` เดิม |
| `figjam-plugin/` | รองรับ section ผัง (ShapeWithText + connector) + section รูป อยู่แล้ว | **ไม่ต้องแก้** — ถ้าพบว่าต้องแก้ ให้หยุดบอกก่อน ถือเป็นความซับซ้อนที่โผล่ใหม่ |
| `test-figjam-plugin.js` · `README.md` | เทส mock Plugin API + ตารางไปป์ไลน์ | เพิ่มเคส section ใหม่ + อัปเดตตาราง |
| `flow-maint-capture.js` 🆕 | — | **ไฟล์ใหม่ไฟล์เดียวของข้อนี้** · เป็นสคริปต์ไล่กดเฉพาะโฟลว์ ใช้ของโฟลว์อื่นแทนไม่ได้ · ก็อปโครงจาก `flow-trips-capture.js` (`capture()` · manifest · การจัด viewport เหมือนกันหมด) |

**12 หน้าจอที่ capture** — ตั้งต้นจากแผน seed `plan-seed-2569-001` (`travelConfirmed: true` อยู่แล้ว ⇒ เฟส 2 ปลดล็อก ไม่ต้อง fast-forward gate เหมือน `flow-trips-capture.js`)

1. รายการแผน — แผนที่พร้อมเข้าเฟส 2
2. เฟส 2 ขั้น 1 — ใบเดินทางรอแจ้ง กรย.
3. กดส่งแจ้งแล้ว (`notified`)
4. `garage.html` ฝั่ง กรย. — ใบที่ถูกแจ้ง
5. กรย. กดยืนยันวางอะไหล่ (`ready`)
6. ขั้น 2 — รายการรถจัดกลุ่มตามใบเดินทาง
7. ฟอร์มรายคัน drill-in — ก่อนทำ
8. ฟอร์มรายคัน — รายการที่ทำจริง + ตัวอย่างน้ำมัน
9. ฟอร์มรายคัน — หลังทำ + ปิดคัน
10. คันที่ "บำรุงรักษาไม่ได้" + ธงรอเลื่อน
11. ขั้น 3 — เอกสาร + ส่งแบบประเมิน · แบบประเมินฝั่งหน่วยงานใน `confirm.html`
12. ขั้น 4 — ทวน + ปิดเฟส → เฟส 3 ปลดล็อก

**ลำดับงาน** — ทำหลังเฟส 2 เดินได้จริงและเทสผ่านแล้วเท่านั้น (capture ต้องมีหน้าจอจริงให้กด)

```bash
python3 -m http.server 8123 --bind 127.0.0.1 &
NODE_PATH=… node figma-export/flow-maint-capture.js
NODE_PATH=… node figma-export/4-figjam-diagram.js \
  --src=Diagram/01-บำรุงรักษาตามวาระ/03-เฟส2-ดำเนินการบำรุงรักษา.md --out=diagram-maint.json
node figma-export/3-figjam-board.js --maint
node figma-export/test-figjam-plugin.js          # mock Plugin API ก่อนเปิด Figma
node figma-export/serve.js                       # แล้วกดในปลั๊กอิน (มือคน)
```

**เกณฑ์ว่าผ่าน** — capture ครบ 12 รูป ไม่มี `errors[]` · `4-figjam-diagram.js` แบบไม่ใส่พารามิเตอร์ยังได้ผลเท่าเดิม (regression) · `test-figjam-plugin.js` ผ่าน · รูปไม่เกิน 4096px ต่อด้าน (สไลซ์อัตโนมัติถ้ายาว)
