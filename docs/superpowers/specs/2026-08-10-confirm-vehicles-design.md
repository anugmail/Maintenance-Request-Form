# Spec — ขั้น "ยืนยันรถเข้าร่วมแผน" (CF) หน้าจริง

วันที่ 10 ส.ค. 2569 · สถานะ: ตกลงกับเจ้าของงานแล้ว รอทำแผน implement

## ปัญหา

เฟส 1 ของโฟลว์บำรุงรักษาตามวาระ ทำแผนเดินทาง (วัน · จุดนัด · เบี้ยเลี้ยง/ที่พัก/ค่าเดินทาง) จาก **จำนวนรถตอนออกเลขงาน** ทั้งที่ยังไม่มีใครยืนยันว่ารถแต่ละคันเข้าบำรุงรักษาได้จริง

เจ้าของงานยืนยัน 10 ส.ค. 2569: *"ต้องรู้จำนวนของรถที่ต้องบำรุงรักษาก่อน"* ⇒ ต้องถามหน่วยงานเจ้าของรถ **ก่อน** วางแผนเดินทาง และ กบค. ต้องเห็นผลตอบกลับ

ขั้นนี้ออกแบบไว้แล้วในรอบ 9 ส.ค. (จอ `1a` + `ต้นทาง` ใน `plan-skeleton.html` · ผัง `Diagram/01-บำรุงรักษาตามวาระ/02-เฟส1-*.md`) แต่ยังเป็น ⬜ **ไม่มีหน้าจริง**

## สิ่งที่จะได้

ขั้นใหม่ในเฟส 1 ที่ กบค. ส่งคำขอยืนยันไปหน่วยงานเจ้าของรถ เห็นผลตอบกลับรายคันแบบรวมศูนย์ ตัดสินคันที่ไม่พร้อมได้เอง แล้วแผนเดินทางจึงเดินต่อจาก **จำนวนคันที่ยืนยันแล้ว**

## 1 · ขอบเขต

**ทำ**
- แทรกขั้น **"ยืนยันรถเข้าร่วมแผน"** เป็นขั้นที่ 2 ของเฟส 1 (`PROC_STEPS` 3 → 4 ขั้น)
- หน้าจริงฝั่ง **กบค.** — ส่งคำขอ · ติดตามผล · ตัดสินรายคัน
- หน้าจริงฝั่ง **หน่วยงานเจ้าของรถ** — `confirm.html` ตอบรายคัน
- เพิ่มฟิลด์ `ownerDept` ให้ vehicle master + ค่าตั้ง `confirmDueDays`
- ผูกขั้นแผนเดินทางให้ใช้เฉพาะคันที่เข้าแผนจริง
- sync `Diagram/` · `skeleton-data.js` · `plan.md`

**ไม่ทำรอบนี้**
- ผูกสิทธิ์รายบุคคล (ใครในหน่วยงานกดได้) — ยังไม่เคาะ ดูข้อ 10
- แจ้งเตือนจริง (email/push) — ต้นแบบใช้ badge + รายการในหน้าเท่านั้น
- ยกคันที่ "เลื่อนรอบหน้า" ไปแผนปีถัดไปอัตโนมัติ
- คำนวณยอดเบี้ยเลี้ยง/ที่พัก/ค่าเดินทางอัตโนมัติจากจำนวนคัน (ของเดิมเป็นช่องกรอกมือ คงไว้)
- สายว่าจ้าง (ต้นแบบยังทำเฉพาะสายตรวจเอง)

## 2 · กติกาที่เคาะกับเจ้าของงาน (10 ส.ค. 2569)

| # | ข้อ | คำตอบ |
|---|---|---|
| 1 | CF เกิดก่อนหรือหลังแผนเดินทาง | **ก่อน** — ต้องรู้จำนวนรถก่อนวางแผน |
| 2 | ใครเป็นผู้ตอบ | **หน่วยงานเจ้าของรถ** (หน่วยงานที่รถคันนั้นอยู่) — ไม่แยกเป็นเจ้าของรถ/กรย. อีก |
| 3 | ไม่ตอบตามกำหนดแล้วยังไง | **ระบบไม่ตัดรถเอง** — ขึ้นป้าย "เลยกำหนด" ให้ กบค. กดตัดสิน เหมือนคันที่ตอบว่าไม่พร้อม |
| 4 | แก้คำตอบได้ถึงเมื่อไหร่ | **จนกว่า กบค. จะยืนยันแผนเดินทาง** (`plan.travelConfirmed === true`) แล้วล็อก |

**หลักที่สืบทอดจากรอบ 9 ส.ค. (ไม่เปลี่ยน)** — คันที่ไม่พร้อม *ค้างไว้ให้ กบค. ตัดสิน* ไม่ตัดอัตโนมัติ

## 3 · ลำดับใน flow

```
เฟส 1:  1. ยืนยันรถเข้าร่วมแผน 🆕 → 2. เบิก/จัดหาอะไหล่ → 3. แผนเดินทาง → 4. ทวน + ยืนยัน
```

🔒 **แก้ 10 ส.ค. 2569 ตามที่เจ้าของงานสั่ง** — เดิมวางยืนยันรถไว้เป็นขั้นที่ 2 (หลังเบิกอะไหล่)
*"เฟสทบทวนและยืนยันต้องเกิดก่อนที่จะเบิกอะไหล่ หลังจากยืนยันครบแล้วถึงจะเริ่มทำเรื่องจัดหาอะไหล่ และถึงไปเริ่มทำแผนการเดินทาง"*

- ขั้น 2 เปิดไม่ได้จนกว่า **ทุกคันมีข้อสรุป** = ตอบว่าพร้อม หรือ กบค. ตัดสินแล้ว
- **จำนวนอะไหล่ที่เบิกคิดจากคันที่ยืนยันแล้วเท่านั้น** ไม่ใช่รถในแผนทั้งหมด — เบิกก่อนยืนยันจะสั่งของเกินให้คันที่ถูกตัด/เลื่อน
- ขั้น "ทวน + ยืนยัน" คงไว้ท้ายสุด (ทวนทั้งเฟสก่อนปิด)
- เฟส 1 ยังถือว่าจบที่ `plan.travelConfirmed === true` เหมือนเดิม — `isPhaseComplete()` ไม่เปลี่ยน

## 4 · โครงข้อมูล

### 4.1 `plan.confirm`

```js
plan.confirm = {
  requestedAt: null,      // null = ยังไม่ส่งคำขอ
  dueAt: null,            // requestedAt + confirmDueDays
  remindedAt: null,       // ครั้งล่าสุดที่ กบค. กดส่งเตือนซ้ำ
  byVehicle: {
    'v-3-1': {
      answer:  'pending', // 'pending' | 'ready' | 'notready'
      reason:  '',        // เหตุผลเมื่อ notready
      meetPoint: '',      // จุดนัดรับที่สะดวก
      by: '', at: '',     // ผู้ตอบ + เวลาตอบล่าสุด
      history: [],        // [{ at, by, from, to, reason }] — ทุกครั้งที่แก้
      verdict: null,      // null | 'keep' | 'drop' | 'defer'  (คำตัดสิน กบค.)
      verdictWhy: '', verdictAt: '',
    },
  },
}
```

### 4.2 ฟังก์ชันคำนวณ — อยู่ใน `mock-yearly.js` (`window.MYD`)

วางไว้ที่นี่ตามแพตเทิร์นเดิมของ `MYD.linesFor()` / `MYD.planLines()` เพื่อให้หน้า กบค. กับหน้าหน่วยงาน **เห็นตัวเลขชุดเดียวกัน** และเทสด้วย node ได้โดยไม่ต้องเปิดเบราว์เซอร์

| ฟังก์ชัน | คืนค่า |
|---|---|
| `confirmStatus(plan, vehicleId, today)` | `'pending'` \| `'ready'` \| `'notready'` \| `'overdue'` — `overdue` = ยัง `pending` และเลย `dueAt` |
| `isVehicleIn(plan, vehicleId, today)` | เข้าทริปไหม — `verdict:'drop'\|'defer'` → false · `verdict:'keep'` → true · ไม่มี verdict แล้ว `answer:'ready'` → true · นอกนั้น false |
| `confirmResolved(plan, vehicleIds, today)` | ทุกคันมีข้อสรุปแล้วไหม — `answer:'ready'` หรือ `verdict !== null` |
| `confirmSummary(plan, vehicleIds, today)` | `{ total, ready, waiting, notready, overdue, joining }` |
| `confirmLocked(plan)` | `plan.travelConfirmed === true` — ล็อกการแก้คำตอบ (กติกาข้อ 4) |

`today` รับเข้ามาเป็นพารามิเตอร์ ไม่เรียก `new Date()` ข้างใน — เทสกรณี "เลยกำหนด" ได้โดยไม่ต้องแก้เวลาเครื่อง

### 4.3 ฟิลด์ใหม่ที่ vehicle master

`vehicle.ownerDept` — ชื่อหน่วยงานเจ้าของรถ · แก้ได้จาก Admin เหมือนฟิลด์อื่น

**ที่มาของค่า** — ยกจาก `hierarchy-data.json` (74 จังหวัด · กฟจ./กฟส. พร้อมขนาด) ที่มีอยู่แล้วในโปรเจกต์ ใช้วิธีเดียวกับตอนเพิ่มยี่ห้อ (ยกของที่มีในโปรเจกต์ ไม่คิดชื่อขึ้นเอง)

⚠️ ชื่อในไฟล์นั้น **สระ า/ำ เพี้ยนจาก font subset ของ PDF** — ไล่แก้เฉพาะชื่อที่ seed ใช้จริง (ไม่กี่สิบชื่อ) ส่วนการเติมครบ 74 จังหวัดยังเป็น backlog เดิมของโปรเจกต์

### 4.4 ค่าตั้งค่า

`MYD.loadSettings()` / `saveSettings()` — key `maintaind.yearly.settings.v1` · `{ confirmDueDays: 7 }` · แก้ได้จาก `admin.html`

โมดูลนี้ยังไม่เคยมีที่เก็บค่าตั้งค่า จึงสร้างใหม่ให้เล็กที่สุดเท่าที่ต้องใช้ — **ไม่ hardcode 7 ในโค้ดหน้าจอ**

### 4.5 Migration

`SCHEMA_VERSION` 6 → **7** (เพิ่ม `ownerDept` + `plan.confirm`) — ของเดิมใน localStorage รีเซ็ตเองตามกลไกที่มีอยู่

`SEED_PLAN` (`MT-2569-Q1-001` · 12 คัน) เพิ่ม `confirm` ที่ **ส่งคำขอแล้วและมีคำตอบกลับมาบางส่วน** เพื่อให้เปิดมาเห็นของจริงทันที: **พร้อม 8 · ไม่พร้อม 2** (พร้อมเหตุผล) · **ยังไม่ตอบ 2**

⚠️ ค่าคงที่ทั้งหมด (รวม `requestedAt`/`dueAt` เป็นวันที่ตายตัวในปีงบ 2569) ตามกติกาเดิมของ `SEED_PLAN` เพื่อให้ลิงก์ `#plan-seed-2569-001` ใช้ได้ตลอด

⇒ เพราะ `dueAt` คงที่และเป็นอดีต **2 คันที่ยังไม่ตอบจะขึ้นสถานะ "เลยกำหนด"** เมื่อเปิดดูวันนี้ — ตั้งใจให้เป็นแบบนั้น เดโมจะได้เห็นทั้งเส้น *ไม่พร้อม* และเส้น *เลยกำหนด* ซึ่งเป็น 2 ทางที่ต้องให้ กบค. ตัดสิน · สถานะ `รอตอบ` (ยังไม่ถึงกำหนด) เห็นได้จากแผนที่สร้างใหม่เอง

## 5 · หน้าจอฝั่ง กบค. (ขั้นที่ 2 ของเฟส 1)

**ก่อนส่งคำขอ** — สรุปว่าจะส่งไปกี่หน่วยงาน กี่คัน · กำหนดตอบกี่วัน · ปุ่ม **"ส่งคำขอยืนยัน"**

**หลังส่งคำขอ**
- แถบสรุป: **ยืนยันแล้ว / รอตอบ / ไม่พร้อม / เลยกำหนด** + วันครบกำหนด
- ตารางรายคัน: ทะเบียน · ยี่ห้อ/รุ่นอุปกรณ์ · เขต · **หน่วยงานเจ้าของรถ** · คำตอบ · เหตุผล · จุดนัดรับ · ตอบเมื่อ · **คำตัดสิน กบค.**
- คันที่ `notready` หรือ `overdue` → ปุ่มตัดสิน **เข้าตามเดิม / ตัดออกจากแผน / เลื่อนรอบหน้า** + ช่องเหตุผล
- ปุ่ม **ส่งเตือนซ้ำ** — ต้นแบบยังไม่มีระบบแจ้งเตือนจริง แค่บันทึก `plan.confirm.remindedAt` แล้วขึ้น toast + แสดงว่าเตือนล่าสุดเมื่อไหร่ (ไม่ลง `history` ของรถ เพราะ `history` เก็บเฉพาะการเปลี่ยนคำตอบ)
- ท้ายหน้าบอกชัด: **เข้าทริปนี้ N คัน** — ตัวเลขที่แผนเดินทางจะใช้

ปุ่ม "ถัดไป" ปิดอยู่จนกว่า `confirmResolved()` เป็นจริง พร้อมข้อความบอกว่าเหลือกี่คันที่ยังไม่มีข้อสรุป

## 6 · หน้าจอฝั่งหน่วยงานเจ้าของรถ — `confirm.html`

ทำตามแพตเทิร์นเดียวกับ `supplies.html` ที่มีอยู่แล้ว (รายการ → เปิดรายใบ → ตอบ) เพื่อไม่สร้างแพตเทิร์นใหม่ในโมดูลเดียวกัน

- **รายการคำขอ** — 1 แถว = 1 หน่วยงาน × 1 แผน · แสดงเลขงาน · จำนวนรถ · ตอบแล้วกี่คัน · กำหนดตอบ · badge `รอตอบ N`
- **เปิดรายใบ** (`#<planId>/<deptSlug>`) — หัวคำขอ (เลขงาน · ชื่อแผน · หน่วยงานผู้ขอ · กำหนดตอบ) + ตาราง **เฉพาะรถของหน่วยงานนี้**: ทะเบียน · ยี่ห้อ · สถานะรถ · **คำตอบ (พร้อม/ไม่พร้อม)** · เหตุผลถ้าไม่พร้อม · จุดนัดรับที่สะดวก
- ช่อง **ผู้ตอบ** (ชื่อ) + ปุ่มส่งคำตอบ
- ตอบแล้วยัง **แก้ได้** จนกว่า `confirmLocked(plan)` — ล็อกแล้วขึ้นข้อความว่าแผนเดินทางยืนยันแล้ว ติดต่อ กบค.
- ทุกการแก้ลง `history[]`

**ต้นแบบไม่มีระบบ login** — หน้ารายการจึงแสดงทุกหน่วยงานที่มีรถในแผน ให้ผู้เดโมเลือกเปิดเอง (แบบเดียวกับที่ mock แจ้งซ่อมสลับบทบาทได้) มีข้อความกำกับว่าของจริงจะเห็นเฉพาะหน่วยงานตัวเอง

## 7 · ผูกกลับเข้าแผนเดินทาง

- ขั้นแผนเดินทาง (เดิมขั้น 2 → เป็นขั้น 3) แสดง **"รถที่เข้าทริปนี้ N คัน"** จาก `isVehicleIn()` พร้อมลิสต์ทะเบียน
- ขั้นทวน + ยืนยัน (เดิมขั้น 3 → ขั้น 4) แสดงจำนวนเดียวกัน และระบุคันที่ถูกตัด/เลื่อนพร้อมเหตุผล
- ยอดเงินยังเป็นช่องกรอกมือเหมือนเดิม — สเปกนี้**ไม่**ทำให้คำนวณอัตโนมัติ แต่วางตัวเลขจำนวนคันไว้ข้างช่องกรอกให้เห็นชัดว่าควรคิดจากกี่คัน

- `confirmSummary` ตัวเลขรวมตรง

**headless Chromium** (ตาม `.claude/skills/verify`) — ไม่มี `pageerror` · ส่งคำขอแล้วสถานะเปลี่ยน · ตอบจาก `confirm.html` แล้วผลไปโผล่ฝั่ง กบค. · ตัดสินคันที่ไม่พร้อมแล้วจำนวน "เข้าทริป" เปลี่ยน · ขั้นแผนเดินทางเปิดไม่ได้จนกว่าจะครบ · ยืนยันแผนเดินทางแล้วหน้าหน่วยงานล็อก · รีโหลดแล้วค่าอยู่ · ลิงก์เมนูทุกหน้าไม่ 404

**mermaid** — `parse()` + `render()` ผ่านครบทุกไฟล์ใน `Diagram/01-บำรุงรักษาตามวาระ/`

## 10 · ยังไม่เคาะ (แสดงไว้ในหน้า ไม่เดาแทน)

## 11 · ข้อควรระวัง

- **verdict ต้องชนะ answer เสมอ** — หน่วยงานตอบ "ไม่พร้อม" แต่ กบค. ตัดสิน `keep` ⇒ เข้าทริป · เขียนเป็นเทสไว้เพราะสลับลำดับ if แล้วพังเงียบ
- **อย่าเขียน `plan.confirm` ลง storage ตั้งแต่เปิดหน้า** — บทเรียนจากบั๊ก `plan-new.html` 8 ส.ค. ที่สร้างแผนร่างเปล่าทุกครั้งที่เปิดหน้า · เขียนเมื่อ กบค. กด "ส่งคำขอยืนยัน" เท่านั้น
- **จำนวนคันมี 2 ความหมาย** — *รถในแผน* (ตอนออกเลขงาน) กับ *รถที่เข้าทริป* (หลัง CF) ต้องแยกป้ายให้ชัดทุกหน้า ไม่งั้นอ่านตัวเลขผิด
- **เลื่อนเลขขั้นของ `PROC_STEPS`** กระทบ `state.sub`, `validateProcSub`, `nextProcSub` (hardcode `>= 3`), `renderProcSubBody`, ป้ายปุ่มขั้นสุดท้าย — ไล่ให้ครบ อย่าแก้แค่ array
