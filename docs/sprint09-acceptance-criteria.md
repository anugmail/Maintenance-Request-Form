## US-S09-01 — Login จริงผ่าน VMS+ / Keycloak

**User story:** ในฐานะผู้ใช้งาน ฉันต้องการเข้าสู่ Maintain-D ผ่านการยืนยันตัวตนของ VMS+ เพื่อใช้งานด้วยบัญชีและสิทธิ์จริง

**ขอบเขต:** Keycloak ยืนยันตัวตน และ UserHub เป็นแหล่งสิทธิ์ตามโน้ตในบอร์ด หน้า SSO เป็นระบบที่มีอยู่แล้ว ใช้ทดสอบการเชื่อมต่อโดยไม่ถือว่าเป็นงานออกแบบ SSO ใหม่

| AC ID | ระดับ | Given / When / Then |
|---|---|---|
| AC-S09-01-01 | R | **Given** ยังไม่ได้เข้าสู่ระบบ **When** เปิดการเข้าสู่ Maintain-D **Then** แสดงทางเข้าสู่ระบบ VMS+ และเข้าสู่กระบวนการ Login จริงได้ โดยไม่มีหน้าเลือก mock user |
| AC-S09-01-02 | D | **Given** อยู่หน้าเข้าสู่ VMS+ **When** เลือก “พนักงาน กฟภ.” **Then** ไปหน้า SSO กฟภ. เพื่อกรอกบัญชี |
| AC-S09-01-03 | R | **Given** บัญชีถูกต้องและมีสิทธิ์ **When** Login สำเร็จ **Then** ได้ token ของผู้ใช้ที่ Login จริง และเข้าสู่หน้า Overhaul ได้ โดยไม่ใช้ identity ของ mock user |
| AC-S09-01-04 | R | **Given** มีบัญชีทดสอบแยก `admin-super`, `general`, `admin-region` **When** Login ทีละบัญชี **Then** ทั้งสามบัญชีเข้าสู่ระบบได้และได้รับ identity/role ตรงกับบัญชีที่ใช้ |
| AC-S09-01-05 | D | **Given** อยู่หน้า SSO **When** กรอกบัญชีหรือรหัสผ่านไม่ถูกต้อง **Then** ไม่เข้าสู่ VMS+ และ SSO แสดง “Invalid username or password.” ตามพฤติกรรมเดิม |
| AC-S09-01-06 | D | **Given** ยืนยันตัวตน SSO สำเร็จแต่บัญชียังไม่มีสิทธิ์เข้า VMS+ **When** กลับจาก SSO **Then** แสดง “คุณไม่มีสิทธิ์เข้าใช้งานระบบ” และ “กรุณาติดต่อผู้ดูแลหากต้องการเข้าใช้งาน” โดยไม่เก็บ token สำหรับใช้งานต่อ ปิดข้อความแล้วยังอยู่หน้าเข้าสู่ระบบ |
| AC-S09-01-07 | P | **Given** ยังไม่ได้ Login **When** เปิด URL รายละเอียด Overhaul/PO โดยตรง **Then** ต้องเข้าสู่กระบวนการ Login ก่อน และไม่แสดงข้อมูลรายละเอียดระหว่างรอ |

**รอยืนยัน:** ระยะเวลา token/session และ refresh token, การกลับหน้าปลายทางหลัง Login, URL ของแต่ละ environment และ CORS ที่จำเป็น หน้าเลือกบัญชี VMS+ เดิมกับหน้าเลือก mock user เป็นคนละส่วน—ข้อสรุปให้เอาออกหมายถึงหน้า mock user

## US-S09-02 — เมนูและข้อมูลตามสิทธิ์

**User story:** ในฐานะเจ้าของรถ/ผู้ดูแลเขต/ผู้ดูแลส่วนกลาง ฉันต้องการเห็นเมนูและรถตามสิทธิ์ เพื่อทำงานกับข้อมูลในความรับผิดชอบ

| AC ID | ระดับ | Given / When / Then |
|---|---|---|
| AC-S09-02-01 | R | **Given** Login จริงสำเร็จ **When** เปิดหน้าใช้งาน **Then** เมนูและรายละเอียดที่เข้าถึงได้สอดคล้องกับสิทธิ์ที่ได้รับจากระบบสิทธิ์ |
| AC-S09-02-02 | R | **Given** ผู้ใช้มี role `general` และผูกหน่วยงานแล้ว **When** เปิดรายการรถ **Then** เห็นเฉพาะรถภายในหน่วยงานของตน |
| AC-S09-02-03 | R | **Given** ผู้ใช้มี role `admin-region` และผูกเขตแล้ว **When** เปิดรายการรถ **Then** เห็นเฉพาะรถภายในเขตของตน |
| AC-S09-02-04 | R | **Given** ผู้ใช้มี role `admin-super` **When** เปิดรายการรถ **Then** เห็นรถทั้งหมดในขอบเขตระบบ |
| AC-S09-02-05 | D | **Given** ผู้ใช้เข้า VMS+ ได้แต่ไม่มีสิทธิ์ Overhaul เช่นมีเพียง `vehicle-user` ตามตัวอย่างในบล็อก A.4 **When** เปิดเมนู **Then** ไม่แสดงเมนู “จัดการงาน Overhaul” โดยไม่ตีความว่าผู้ใช้ไม่มีสิทธิ์เข้า VMS+ ทั้งระบบ |
| AC-S09-02-06 | D | **Given** ผู้ใช้ไม่มีสิทธิ์ Overhaul **When** เปิด URL Overhaul โดยตรง **Then** ไม่แสดงข้อมูลแผนหรือรถแม้บางส่วน และแจ้งว่าไม่มีสิทธิ์เข้าถึง |
| AC-S09-02-07 | P | **Given** ผู้ใช้มีสิทธิ์เฉพาะหน่วยงาน/เขต **When** เปลี่ยน ID ใน URL หรือเรียกข้อมูลรถนอกขอบเขต **Then** ระบบปฏิเสธการเข้าถึงและไม่ส่งข้อมูลรถนั้นกลับ |

**Dependency:** ต้องมีชุดข้อมูลผูกผู้ใช้→หน่วยงาน/เขต→รถ และ mapping role กับเมนูซ่อม/บำรุงรักษา/Overhaul ก่อน QA ตรวจรับ; บอร์ดยังไม่ได้ระบุสิทธิ์สร้าง/แก้ไข/ลบราย role จึงไม่อนุมานว่า role ที่อ่านได้จะแก้ไขได้

## US-S09-03 — Notification ตามเหตุการณ์ธุรกิจ

**User story:** ในฐานะหน่วยงานต้นทางและ กบค. ฉันต้องการรับแจ้งเตือนเมื่อขั้นตอนสำคัญสำเร็จ เพื่อทราบสถานะและดำเนินการต่อ

**ช่องทางตามข้อสรุป [R]:** VMS+ (in-app), PEA Life, Work-D และ SMS โดยไม่รวม Firebase; SMS ส่งเฉพาะ Vendor ที่ `is_employee = false` ไม่ส่งให้พนักงาน กฟภ. ทั้งนี้ต้องยืนยัน mapping ผู้รับแต่ละช่องทางก่อนทดสอบครบวงจร

| AC ID | ระดับ | Given / When / Then |
|---|---|---|
| AC-S09-03-01 | R | **Given** มีการนัดหมายรถเข้าอู่ **When** ส่งนัดหมายสำเร็จ **Then** สร้างการแจ้งเตือนถึงหน่วยงานต้นทางสำหรับรายการนัดหมายนั้น |
| AC-S09-03-02 | R | **Given** หน่วยงานต้นทางได้รับนัดหมาย **When** ต้นทางยืนยันนัดหมายสำเร็จ **Then** สร้างการแจ้งเตือนถึง กบค. ว่าหน่วยงานต้นทางยืนยันแล้ว |
| AC-S09-03-03 | R | **Given** มีงานตรวจรับรถ **When** ตรวจรับรถสำเร็จ **Then** สร้างการแจ้งเตือนถึงหน่วยงานต้นทางของรถนั้น |
| AC-S09-03-04 | R | **Given** งานพร้อมยืนยันขั้นตอนที่ 7 **When** ยืนยันการส่งอนุมัติสำเร็จ **Then** สร้างการแจ้งเตือนปิดงานถึงหน่วยงานต้นทาง โดยไม่รอผู้อนุมัติ |
| AC-S09-03-05 | R | **Given** เกิดเหตุการณ์ใดเหตุการณ์หนึ่งข้างต้นและทราบผู้รับ **When** ส่งแจ้งเตือน **Then** รองรับการส่งผ่าน VMS+, PEA Life และ Work-D ตามผู้รับที่เกี่ยวข้อง และใช้ SMS เฉพาะผู้รับ Vendor ที่มี `is_employee = false` |
| AC-S09-03-06 | R | **Given** ผู้รับเป็นพนักงาน กฟภ. (`is_employee = true`) **When** เกิดเหตุการณ์แจ้งเตือน **Then** ไม่ส่ง SMS ให้ผู้รับรายนั้น |
| AC-S09-03-07 | R | **Given** สร้าง notification ของ Overhaul **When** บันทึกแจ้งเตือน **Then** มี `notify_type` ให้แยกประเภทงาน Overhaul ออกจากประเภทงานอื่นได้; ค่าจริงและชื่อประเภทงานซ่อมใหญ่รอยืนยัน |
| AC-S09-03-08 | P | **Given** การบันทึกขั้นตอนธุรกิจไม่สำเร็จ **When** ระบบตอบกลับว่าล้มเหลว **Then** ไม่สร้างแจ้งเตือนที่ระบุว่าขั้นตอนนั้นสำเร็จ |
| AC-S09-03-09 | P | **Given** เหตุการณ์หนึ่งส่งไปบางช่องทางสำเร็จแต่บางช่องทางล้มเหลว **When** ตรวจสอบผลส่ง **Then** แยกผลรายช่องทางได้ และไม่เปลี่ยนผลธุรกิจที่บันทึกสำเร็จแล้วเป็นล้มเหลวเพียงเพราะการส่งแจ้งเตือนล้มเหลว; วิธี retry รอยืนยัน |

**ข้อความตามบอร์ด [R] — ตัวแปรต้องใช้ข้อมูลของรายการจริง:**

| เหตุการณ์ | ข้อความ |
|---|---|
| นัดหมายรถเข้าอู่ | “นัดหมาย {ข้อมูลสำคัญ เช่นเลขแผนหรือ PO} สำเร็จ” |
| ต้นทางยืนยันนัดหมาย | “หน่วยงาน {สังกัด} ของ {ข้อมูลสำคัญ เช่นเลขแผนหรือ PO} ยืนยันนัดหมายแล้ว” |
| ตรวจรับรถสำเร็จ | “ยืนยันรับรถสำเร็จ” |
| ยืนยันขั้นตอนที่ 7 | “ปิดงาน {ข้อมูลสำคัญ เช่นเลขแผนหรือ PO} เรียบร้อยแล้ว” |

**รอยืนยัน:** จะใช้เลขแผน, PO, ทะเบียนรถ หรือหลายค่าร่วมกันในข้อความ; ผู้รับเป็นรายบุคคลหรือกลุ่มหน่วยงาน; แหล่ง EmployeeId ของ PEA Life; ผู้รับ Work-D; endpoint และสัญญาข้อมูลที่ใช้งานจริง; กรณี Vendor ไม่มีเบอร์หรือ `is_employee` ไม่ทราบค่า ไม่มีการถือว่าค่าว่างเท่ากับ false

## US-S09-04 — รายการแจ้งเตือนใน VMS+ และลิงก์รายละเอียด

| AC ID | ระดับ | Given / When / Then |
|---|---|---|
| AC-S09-04-01 | R | **Given** มีข้อความที่ยังไม่อ่าน **When** แสดงไอคอนแจ้งเตือน **Then** แสดง badge dot สีเขียว |
| AC-S09-04-02 | R | **Given** มีรายการแจ้งเตือน **When** เปิดรายการ **Then** รายการที่ยังไม่ได้กดมีพื้นหลังสีเทา และรายการที่กดอ่านแล้วมีพื้นหลังสีขาว |
| AC-S09-04-03 | R | **Given** กำลังแสดงรายการแจ้งเตือน **When** กดรายการหนึ่ง **Then** เปิดหน้ารายละเอียดที่สัมพันธ์กับแจ้งเตือนนั้น เช่นรายละเอียด Overhaul หรือ PO โดยใช้ ID ใน URL เป็นพารามิเตอร์เพื่อดึงข้อมูล |
| AC-S09-04-04 | R | **Given** กดอ่านรายการที่ยังไม่อ่าน **When** กลับมาดูรายการ **Then** รายการนั้นมีสถานะอ่านแล้ว และเมื่อไม่มีข้อความที่ยังไม่อ่าน badge dot หายไป |
| AC-S09-04-05 | R | **Given** มีรายการแจ้งเตือน **When** กด “ล้างข้อความแจ้งเตือน” **Then** เคลียร์รายการแจ้งเตือนทั้งหมดของผู้ใช้และซ่อน badge dot |
| AC-S09-04-06 | R | **Given** ไม่มีรายการแจ้งเตือนหรือถูกล้างแล้ว **When** เปิดรายการ **Then** แสดงสภาพรายการว่างและไม่มี badge dot |
| AC-S09-04-07 | P | **Given** URL รายละเอียดมี ID ที่ถูกต้องและผู้ใช้มีสิทธิ์ **When** เปิด URL โดยตรงหรือ refresh หน้า **Then** โหลดรายละเอียดรายการเดิมได้โดยไม่อาศัยการคลิกมาจากหน้ารายการ |
| AC-S09-04-08 | P | **Given** ปลายทางถูกลบ ไม่มีอยู่ หรือผู้รับไม่มีสิทธิ์ **When** กดแจ้งเตือน **Then** แจ้งว่าไม่สามารถเปิดรายละเอียดได้และไม่เปิดเผยข้อมูลที่ไม่มีสิทธิ์ |

**รอยืนยัน:** ล้างรายการหมายถึงซ่อนสำหรับผู้ใช้หรือลบข้อมูลจริง, การคงสถานะอ่าน/ล้างเมื่อ refresh หรือ Login ใหม่, สีวงขอบไอคอนและข้อความ empty state, ลิงก์ปลายทางของแจ้งเตือนแต่ละเหตุการณ์

## US-S09-05 — เตือนก่อนสิ้นสุดประกัน

**User story:** ในฐานะเจ้าของรถ กรย. และ กบค. ฉันต้องการรับแจ้งเตือนก่อนประกันงานซ่อมสิ้นสุด เพื่อมีเวลาตรวจสอบรถ

**กติกาจากบอร์ด:** หัวข้อเดิมเขียน “ก่อนหมดสัญญา” แต่คำอธิบายระบุชัดให้นับจาก **วันสิ้นสุดประกัน** จึงใช้วันสิ้นสุดประกันเป็นฐานของ AC ชุดนี้ ไม่ใช้วันสิ้นสุดสัญญา PO

| AC ID | ระดับ | Given / When / Then |
|---|---|---|
| AC-S09-05-01 | R | **Given** รถมีวันสิ้นสุดประกัน **When** ถึงวันก่อนสิ้นสุดประกัน 30 วัน **Then** สร้างแจ้งเตือนล่วงหน้า 30 วันหนึ่งครั้งสำหรับรอบประกันนั้น |
| AC-S09-05-02 | R | **Given** รถมีวันสิ้นสุดประกัน **When** ถึงวันก่อนสิ้นสุดประกัน 15 วัน **Then** สร้างแจ้งเตือนล่วงหน้า 15 วันหนึ่งครั้งสำหรับรอบประกันนั้น แม้เคยแจ้งที่ 30 วันแล้ว |
| AC-S09-05-03 | R | **Given** เข้าเงื่อนไขเตือน **When** กำหนดผู้รับ **Then** แจ้งเจ้าของรถ กรย. และ กบค. ที่เกี่ยวข้องกับรถนั้น |
| AC-S09-05-04 | R | **Given** สร้างแจ้งเตือนสิ้นสุดประกัน **When** แสดงข้อความ **Then** หัวข้อเป็น “แจ้งวันสิ้นสุดประกัน” และรายละเอียดเป็น “แจ้งวันสิ้นสุดประกัน วันที่ {วันสิ้นสุดประกัน} ของรถ {เลขทะเบียน} โปรดตรวจสอบความเรียบร้อย” โดยแทนค่าจริง |
| AC-S09-05-05 | R | **Given** เคยสร้างแจ้งเตือนระยะ 30 หรือ 15 วันของรอบประกันนั้นแล้ว **When** กระบวนการตรวจสอบทำงานซ้ำ **Then** ไม่สร้างแจ้งเตือนระยะเดิมซ้ำ |
| AC-S09-05-06 | P | **Given** รถไม่มีวันสิ้นสุดประกัน **When** ตรวจเงื่อนไขแจ้งเตือน **Then** ไม่คำนวณวันเตือนจากวันที่สมมติและไม่ใช้วันสิ้นสุด PO แทนโดยอัตโนมัติ |

**ตัวอย่างตรวจรับ [P]:** หากวันสิ้นสุดประกันเป็น 31/12/2569 จะเข้าเงื่อนไข 30 วันในวันที่ 1/12/2569 และ 15 วันในวันที่ 16/12/2569 โดยเสนอให้นับวันปฏิทินตามเวลาไทย

**รอยืนยัน:** ช่องทางแจ้งเตือนของประกัน (ไม่อนุมานว่าใช้ทุกช่องทางเช่นเดียวกับ 4 เหตุการณ์), เวลารันงาน, timezone, วิธีชดเชยเมื่อระบบหยุดทำงาน, การแจ้งย้อนหลังเมื่อเพิ่งบันทึกประกัน, การแก้วันสิ้นสุดประกันหลังเคยส่ง และเจ้าของรถหมายถึงผู้ใช้หรือผู้รับแทนหน่วยงานใด

| Q-08 | ชื่อปุ่มและสถานะหลังยกเลิกการรอผู้อนุมัติ | หน้าจอและ Dashboard ต้องตรง workflow ใหม่ |

## หลักฐานที่ควรใช้ตรวจรับ

- Login จริงครบ 3 role พร้อมข้อมูลทดสอบรถในหน่วยงานตนเอง ต่างหน่วยงานในเขตเดียวกัน และต่างเขต
- หลักฐานเหตุการณ์ธุรกิจสำเร็จ→ผู้รับ→ผลส่งรายช่องทาง ครบ 4 เหตุการณ์ พร้อมกรณีพนักงานไม่รับ SMS
- รายการแจ้งเตือนที่ยังไม่อ่าน อ่านแล้ว ล้างทั้งหมด และลิงก์รายละเอียด Overhaul/PO
- ข้อมูลประกันก่อนครบ 30 วัน ครบ 30 วัน ครบ 15 วัน และรันซ้ำ เพื่อยืนยันส่งครั้งเดียวต่อระยะ
- งานขั้นตอนที่ 7 ที่ยืนยันสำเร็จและล้มเหลว เพื่อยืนยันว่าปิดงานตามผลบันทึกและไม่มีขั้นตอนรอผู้อนุมัติ
- รายการ [D] ทดสอบเมื่อทีมยืนยันให้อยู่ใน Sprint; รายการ [P] ใช้ตรวจรับเมื่อทีมรับรองแล้ว
