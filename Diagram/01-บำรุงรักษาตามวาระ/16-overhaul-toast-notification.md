# Overhaul: Toast และ Notification (สเปกแยก 20 ต.ค. 2569)

เจ้าของงานสั่ง 20 ต.ค. 2569: ออกแบบ toast และ notification ของ Overhaul แยกเป็นอีกเรื่อง ไม่รวมกับของเดิม (งานซ่อมและบำรุงรักษาตามวาระ) อ่าน component ของไลบรารีแล้วออกแบบ แยกให้ชัดว่าส่วนไหนคือ toast ส่วนไหนคือ notification

ที่มา: component ในไลบรารี VMS Plus (ไฟล์ Component ที่ดัมป์ไว้ใน figma-export/out/figma-dump/component) คือ Notification (หน้า Notifications), Alert (หน้า Alerts), Notification card กับ Nav button ใน Header navigation, และ Toast ที่ไลบรารียังไม่ทำเสร็จ, หลักการ UX-7 ใน plan.md, AC ของ Overhaul [15-overhaul-AC.md](15-overhaul-AC.md), ตารางสิทธิ์ [13-overhaul-สิทธิ์ตาม-mock-v2.tsv](13-overhaul-สิทธิ์ตาม-mock-v2.tsv)

ของเดิมที่ไม่แตะ: งานซ่อมกำหนดไว้ใน AC ว่า "แจ้งเตือนในระบบอย่างเดียว ไม่ส่ง SMS หรืออีเมล" และ design system มี .notif (Notification Success/Error มุมขวาล่าง 4 วินาที) ตั้งแต่ 19 ต.ค. 2569 บำรุงรักษาตามวาระมี Notification ของตัวเองใน [14-บำรุงรักษา-userflow.md](14-บำรุงรักษา-userflow.md) สเปกนี้ไม่รวมสองโฟลว์นั้น

## 0. แยกให้ชัดก่อน: สามอย่างที่มักเรียกปนกัน

| | Toast | Notification | ข้อความค้างในหน้า (Alert) |
|---|---|---|---|
| คืออะไร | ผลของสิ่งที่ "ฉัน" เพิ่งกด | ข่าวว่า "อีกฝ่าย" หรือ "ระบบ" ทำอะไรที่ฉันต้องรู้หรือต้องทำต่อ | สถานะที่ค้างอยู่และต้องเห็นตลอดบนหน้านั้น |
| ใครเห็น | คนที่กดเท่านั้น | ผู้รับที่กำหนด (กบค. หรือหน่วยงานเจ้าของรถ) | ทุกคนที่เปิดหน้านั้น |
| อยู่นานแค่ไหน | ชั่วคราว หายเอง | เก็บในกระดิ่งจนกว่าจะลบ | จนกว่าสถานะจะเปลี่ยน |
| ต้องกดไปไหนไหม | ไม่ต้อง | ต้อง กดแล้วไปหน้าที่เกี่ยว | อาจมีปุ่มในตัว |
| ตัวอย่างใน Overhaul | "การสร้างแผน overhaul สำเร็จ" | "หน่วยงานปฏิเสธนัดนำรถ 72-6648 เข้าอู่" | "รอหน่วยงานเจ้าของรถตอบกลับ" ในขั้นนัดหมาย |
| component ไลบรารี | Notification (Type Success หรือ Error, Breakpoint Desktop หรือ Mobile) | Nav button Indicator ที่กระดิ่ง และ Notification card | Alert (Color Success, Warning, Error, Info, Brand, Gray) |

หมายเหตุเรื่องชื่อ: ไลบรารีตั้งชื่อ component แจ้งผลว่า "Notification" ส่วน "Toast" ของไลบรารี (แถบเข้ม 468 x 56 มีปุ่มกลุ่ม) ยังไม่เสร็จและไม่มีหน้าจอไหนใช้ (บันทึกไว้ใน design-system/components.css) สเปกนี้จึงเรียกตามหน้าที่ คือ toast = component Notification และ notification = กระดิ่งกับ Notification card ถ้าทีมออกแบบทำ Toast ของไลบรารีเสร็จค่อยย้าย

### 1.3 สิ่งที่ไม่ใช่ toast แม้จะหน้าตาคล้าย

- ข้อความใต้ช่องเมื่อกรอกไม่ครบ เช่น "กรุณาระบุชื่อแผน" (เป็น validation ของช่อง)
- modal ยืนยันการออก ยืนยันการลบ ยืนยันการแก้ไข (เป็นคำถามก่อนทำ)
- ข้อความในหน้าว่าง เช่น "ยังไม่มีแผน Overhaul" (เป็น empty state)
- ข้อความ "รอหน่วยงานเจ้าของรถตอบกลับ" และ "หน่วยงานปฏิเสธนัดหมาย" ในหน้างานรายคัน (เป็น Alert ค้างในหน้า ดูหัวข้อ 3)

|---|---|---|

## 3. ข้อความค้างในหน้า (Alert) ที่ Overhaul ใช้ เพื่อกันสับสน

ไม่ใช่ toast และไม่ใช่ notification แต่ใช้ในหน้างานรายคันคู่กับสองอย่างข้างบน

| สถานะ | component | ข้อความ |
|---|---|---|
| รอหน่วยงานตอบรับนัด (ขั้นที่ 1 และ 5) | Alert Color = Info หรือส่วน "รอตอบกลับจากหน่วยงาน" ของคอมโพเนนต์นัดหมาย | รอหน่วยงานเจ้าของรถตอบกลับ ส่งนัดหมายแล้ว [วัน] แก้ไขนัดหมายได้จนกว่าหน่วยงานจะตอบรับ |
| หน่วยงานปฏิเสธนัด (ขั้นที่ 1 และ 5) | Alert Color = Warning หรือส่วน "ผลตอบกลับ" ของคอมโพเนนต์นัดหมาย | หน่วยงานปฏิเสธนัดหมาย หมายเหตุ [ข้อความจากหน่วยงาน] |
| ปิดงานแล้ว (ขั้นที่ 6) | Alert Color = Success | ปิดงานแล้ว [วัน] รถคันนี้จบรอบ Overhaul |

## 4. คำถามที่ต้องเคาะกับเจ้าของงาน

1. ข้อความ toast ที่ userflow ไม่ได้ให้คำ (T2 T3 T5 T6 T8 ถึง T13 T15) ใช้ตามร่างนี้ได้ไหม
2. toast ไม่สำเร็จ ให้ค้างจนกดปิดตามที่เสนอ หรือหายเองเหมือนสำเร็จ
3. ระยะเวลา toast สำเร็จ 4 วินาที (ตาม design system) หรือ 5 วินาที (ตามหลักการ)
4. notification ช่องทางในระบบอย่างเดียว หรือเพิ่มอีเมลสำหรับหน่วยงานเจ้าของรถ
5. ผู้รับฝั่ง กบค. คือ กบค. ทั้งกอง หรือเฉพาะผู้ประสานงานที่ระบุในนัด
6. N1 N5 N6 N10 N11 N13 ที่เสนอเพิ่ม เอาหรือไม่เอา
7. N12 เตือนใกล้วันนัด ล่วงหน้ากี่วัน กี่ครั้ง (คำถามเดียวกับงานซ่อมที่ยังค้าง)
8. หน้าจอฝั่งหน่วยงานเจ้าของรถสำหรับกดตอบรับนัด (ปลายทางของ N2 N7) ยังไม่มีใน userflow ต้องออกแบบเพิ่มไหม
