## B. Business AC (มุม BA)

### B1. Happy Path

```gherkin
Scenario: AC-01 กบค. สร้างแผน Overhaul สำเร็จ
  Given กบค. อยู่ที่เมนู "จัดการงาน Overhaul" และมีหนังสืออนุมัติหลักการกับเอกสารอนุมัติงบในมือ
  When  กบค. กด "สร้างแผน Overhaul" กรอกชื่อแผน ประจำปีงบประมาณ วงเงินอนุมัติ (บาท) แนบหนังสืออนุมัติหลักการและเอกสารอนุมัติงบครบ แล้วกด "บันทึก"
  Then  ระบบสร้างแผนใหม่ 1 แผน สถานะ "รอเลข PO" ขึ้นแถวบนสุดของรายการ
  And   แสดง toast "สร้างแผน Overhaul {เลขแผน} สำเร็จ"
  And   เปิดดูหน้ารายละเอียดแผนได้ทันที
```

⚠️ **ยังไม่เคาะ (toast ข้อความสร้างแผน)** — เอกสารนี้ลอกข้อความ toast มาจาก `15-overhaul-AC.md` ว่า `"สร้างแผน Overhaul {เลขแผน} สำเร็จ"` แต่คอมโพเนนต์ toast ในบอร์ด Refinement 29 oct 2026 (เฟรม B.6) แสดงข้อความสั้นกว่าคือ `"สร้างแผน Overhaul สำเร็จ"` ไม่มีตัวแปร `{เลขแผน}` แทรก — อาจเป็นแค่ mockup ที่ยังไม่ผูกตัวแปรจริง ไม่ใช่ spec สุดท้าย ยังไม่เคาะว่าอันไหนถูก ต้องยืนยันกับทีมก่อนตัดสินใจ

  And   แสดงปุ่ม "ล้างคำค้นและตัวกรอง" ช่องค้นหาและปุ่มตัวกรองคงค่าที่พิมพ์/เลือกไว้ ไม่มีการแบ่งหน้าในสภาพนี้

Scenario: AC-08 หน้ารายการยังไม่มีแผนเลยในขอบเขตของ role นั้น
  Given ไม่มีแผนเลยในขอบเขตของ role นั้น และยังไม่ได้พิมพ์คำค้นหรือเลือกตัวกรอง
  When  เปิดหน้า "จัดการงาน Overhaul"
  Then  แทนที่ตารางด้วยข้อความ "ยังไม่มีแผน Overhaul" ข้อความรอง "สร้างแผน Overhaul เพื่อเพิ่ม Purchase Order และติดตามสถานะซ่อมของรถแต่ละคัน"
  And   แสดงปุ่ม "สร้างแผน Overhaul" เฉพาะ role กบค. — role อื่นเห็นแค่ข้อความ ไม่มีปุ่ม
  And   ไม่มีช่องค้นหา ปุ่มตัวกรอง และการแบ่งหน้าในสภาพนี้

## D. ส่วนประกอบท้าย

**Out of Scope**

- หน้าจอฝั่งหน่วยงานเจ้าของรถสำหรับดูแผน (ยังไม่มี userflow ฝั่งหน่วยงานเลย — เป็นคำถามรวมข้อ 2 ของ `15-overhaul-AC.md`)
- การเชื่อม Smart Inventory สำหรับ "อะไหล่ที่ใช้" (ยังจองไว้เฉยๆ ตาม userflow ไม่ใช่เชื่อม API จริง)

**Assumptions**

- หนังสืออนุมัติหลักการและเอกสารอนุมัติงบ ผ่านการอนุมัติจากหน่วยงานที่เกี่ยวข้องมาก่อนแล้วนอกระบบ ก่อนเริ่มสร้างแผน
- เลข WBS ที่กรอกอ้างอิงงบที่อนุมัติไว้แล้วใน SAP (ไม่ validate กับ SAP แบบ real-time ในขั้นนี้ — ไม่มีเอกสารยืนยันว่ามี integration นี้)

**สิ่งที่ยังไม่ครบ — ต้องไปหาอะไรมาเพิ่ม**

- [ ] ยืนยัน Priority (Must/Should/Could) กับ PO — ไม่มีแหล่งอ้างอิงในเอกสารที่มีอยู่
- [ ] ยืนยันงวดส่งมอบ/JO ที่ผูกกับฟีเจอร์นี้ — ไม่มีเอกสารระบุไว้
- [ ] เคาะชื่อสถานะแผนทางการชุดสุดท้าย (จอจริง 3 ค่า "รอเลข PO/รอดำเนินการ/เสร็จสิ้น" vs ชีตเดิม "กำลังดำเนินการ PO/อนุมัติ PO" vs สถานะรายคัน 11 ค่า) — กระทบ enum บน `plan_status` และข้อความ notification
- [ ] เคาะที่มาของ "ประเภทงบ" (งบลงทุน/งบทำการ) ว่าเป็น enum ใหม่หรือค่าคงที่ตายตัว — ปัจจุบันไม่มี column รองรับ
- [ ] เคาะว่าช่อง "ประจำปีงบประมาณ" บังคับให้ผู้ใช้เลือกเองหรือใช้ค่าตั้งต้น (ปี พ.ศ. ปัจจุบัน) ไปเลยได้ — ไม่มี error message ระบุไว้ถ้าไม่เลือก
- [ ] หารูปแบบการรันเลขที่แผน (`plan_no`) จริงจากทีม backend
- [ ] หาตัวเลขขนาดไฟล์สูงสุดต่อไฟล์ที่แนบ ("ตามเกณฑ์เดิมของระบบ" ไม่ได้ระบุตัวเลข)

- [ ] เคาะว่าลบแผนที่มี PO และรถกำลังซ่อมอยู่ได้ไหม และลบแล้วกู้คืนได้ไหม

2. งวดส่งมอบ/JO → จัดอยู่ JO เดียวกับ US-OH-02 ถึง 08 ทั้งชุด เหตุผล: เป็น flow ต่อเนื่องเดียวกันตั้งแต่สร้างแผนถึงปิดงาน แยก JO กลางวงจรจะทดสอบ end-to-end ไม่ได้ก่อนส่งมอบ
3. ชื่อสถานะแผนทางการ → ใช้ชุดจากจอจริง **"รอเลข PO / รอดำเนินการ / เสร็จสิ้น"** เหตุผล: เป็นชุดที่เจ้าของงานยืนยันจากจอจริงล่าสุด (21 ต.ค.) และบอร์ด Refinement 29 oct 2026 ก็ใช้ 2 ใน 3 ค่านี้ซ้ำ (รอดำเนินการ/รอเลข PO) สอดคล้องกันข้ามเวลา ส่วนชีตเดิม ("กำลังดำเนินการ PO"ฯลฯ) ถือเป็นฉบับร่างก่อนจอจริง
4. ที่มาของ "ประเภทงบ" → เป็น **ค่าคงที่ตายตัว "งบลงทุน"** ในเฟสแรก ไม่ใช่ enum ใหม่ เหตุผล: ทั้งฟอร์มสร้าง/แก้ไขไม่มีช่องกรอกเลยทั้งสองรอบที่ตรวจสอบ (21 ต.ค. และบอร์ด 29 oct 2026) และ mock ทุกแถวเป็นค่าเดียวกันหมดทั้งสองรอบ — ถ้าต้องรองรับ "งบทำการ" จริงในอนาคตค่อยเพิ่ม enum ทีหลัง
5. "ประจำปีงบประมาณ" บังคับเลือกเองไหม → **ไม่บังคับ** ใช้ค่าตั้งต้น = ปี พ.ศ. ปัจจุบันได้เลย เหตุผล: มี default เสมอและไม่มี error message ระบุไว้ในทุกแหล่งที่ตรวจสอบ ถ้าบังคับจริงปกติต้องมี error message กำกับเหมือนฟิลด์บังคับอื่น
6. รูปแบบ `plan_no` → ใช้ตามที่ backend ยืนยันแล้ว (`ORZ690000X` จาก `FormatPlanNo`) ไม่ต้องรอ เหตุผล: เป็นโค้ดจริงที่ implement แล้ว ไม่ใช่ข้อเสนอ — ส่วนจอ mock ที่ยังไม่ตรง (Z69000X/ตัวเลขล้วน) ให้แจ้งทีมดีไซน์อัปเดตจอให้ตรง backend แทน
7. ขนาดไฟล์สูงสุดต่อไฟล์ → เสนอ **10MB/ไฟล์** เป็นค่าเริ่มต้นที่ปลอดภัย เหตุผล: สอดคล้องกับแนวทาง BR-02 ของ US-OH-06 ที่บอกให้ "ใช้เงื่อนไขการอัปโหลดเดียวกับฟีเจอร์แจ้งซ่อมเดิม" — ให้ยืนยันตัวเลขจริงจากทีม infra ก่อน แต่ใช้ 10MB ตั้งต้นในการพัฒนาได้
8. จอฝั่งหน่วยงานเจ้าของรถ → **ยังไม่ทำในเฟสนี้** เหตุผล: หน่วยงานไม่มีสิทธิ์เห็นแผนจนกว่าจะมี PO แรกอยู่แล้วตาม B5 ให้หน่วยงานเห็นผ่าน notification + หน้างานรายคันที่มีอยู่แล้วไปก่อน
9. แก้ไขแผนได้ในสถานะไหน → แก้ไขได้ทั้ง "รอเลข PO" และ "รอดำเนินการ" (ตรงกับที่ Gherkin AC-02 ระบุอยู่แล้ว) แต่ **ห้ามแก้ไขเมื่อ "เสร็จสิ้น"** เหตุผล: ปิดงานแล้วไม่ควรแก้ย้อนหลัง สอดคล้องกับหลักการ "ปิดแล้วแก้ไม่ได้อีก" ที่ใช้ซ้ำทั่วทั้งเอกสารนี้ (US-OH-03 BR-05, US-OH-05 BR-03, US-OH-08 BR-03)
10. ลบแผนที่มี PO/รถกำลังซ่อม → **ไม่อนุญาต** ถ้ามี PO ที่มีรถสถานะอื่นที่ไม่ใช่ "ปิดงานแล้ว" ทั้งหมด เหตุผล: ป้องกันลบงานที่กำลังดำเนินอยู่ · กู้คืนได้ไหม → **ไม่ต้องรองรับ** เพราะ C5 ยืนยันแล้วว่าไม่เก็บ audit log การลบ ถ้าไม่มี log ก็ยากจะกู้คืนอย่างมีความหมาย
11. Performance SLA → ใช้มาตรฐานรวมโครงการ TOR ข้อ 19 ไปก่อน ไม่ต้องตั้งตัวเลขเฉพาะ เหตุผล: ปริมาณธุรกรรมของฟีเจอร์นี้ต่ำ (สร้าง/แก้ไข/ลบแผนไม่บ่อย ไม่ใช่ high-throughput endpoint)

## B. Business AC (มุม BA)

### B1. Happy Path

```gherkin
Scenario: AC-01 กบค. สร้าง Purchase Order สำเร็จ
  Given กบค. เปิดหน้ารายละเอียดแผน
  When  กบค. กด "PO" กรอกชื่อ PO เลือกศูนย์บริการ/อู่ เลือกรถอย่างน้อย 1 คัน แนบใบสั่งจ้าง แล้วกด "บันทึก"
  Then  ระบบสร้าง PO ใหม่ในแผน รถทุกคันใน PO เริ่มงานที่ขั้นที่ 1 สถานะ "รอนัดหมายเข้าอู่"
  And   ถ้าเป็น PO ใบแรกของแผน สถานะแผนเปลี่ยนเป็น "รอดำเนินการ"
  And   แสดง toast "การสร้าง purchase order สำเร็จ"
  And   กลับหน้ารายละเอียดแผนและเห็น PO ใหม่ในตาราง
```

### B2. Alternative Flow

```gherkin
Scenario: AC-02 กบค. แก้ไข PO เพิ่มรถเข้าไปอีก
  Given มี PO อยู่แล้วในแผน
  When  กบค. เปิดฟอร์มแก้ไข PO เพิ่มรถอีกคัน แล้วกด "บันทึก" และยืนยันใน modal "ยืนยันการแก้ไข PO"
  Then  รถที่เพิ่มเข้ามาใหม่เริ่มงานที่ขั้นที่ 1 เหมือนรถเดิมในแผน
  And   จำนวนรถในตาราง PO และในแผนอัปเดต
  And   แสดง toast "บันทึกการแก้ไข PO สำเร็จ"
```

### B3. Exception / Negative Flow

```gherkin
Scenario: AC-03 กบค. กดบันทึก PO โดยกรอกข้อมูลไม่ครบ
  Given กบค. อยู่ในฟอร์มสร้าง/แก้ไข PO
  When  กบค. กด "บันทึก" โดยยังไม่กรอกชื่อ PO ยังไม่เลือกศูนย์บริการ/อู่ หรือยังไม่แนบใบสั่งจ้าง
  Then  ระบบไม่บันทึกข้อมูล
  And   แสดงข้อความใต้ช่องที่ขาดตรงตัว เช่น "กรุณาระบุชื่อ Purchase Order", "กรุณาเลือกศูนย์บริการ/อู่", "กรุณาแนบใบสั่งจ้าง"

Scenario: AC-04 กบค. เปิดฟอร์มสร้าง PO จากแผนที่ถูกลบไปแล้ว
  Given แผนต้นทางถูกลบไปแล้ว
  When  กบค. เปิดฟอร์มสร้าง PO ของแผนนั้น
  Then  ระบบไม่เปิดฟอร์ม
  And   แสดง toast "ไม่พบแผน"
```

- [ ] BR-02 ปุ่มบันทึกต้อง disable จนกรอกฟิลด์บังคับครบ (ชื่อ PO, ศูนย์บริการ/อู่, ใบสั่งจ้าง)

## D. ส่วนประกอบท้าย

**Out of Scope**

- การรองรับ PO ที่มีศูนย์บริการ/อู่มากกว่า 1 แห่งต่อใบ (ปัจจุบัน schema เป็น 1:1 vendor ต่อ PO)
- การกรอก/ตรวจสอบมูลค่า PO (บาท) — ไม่มีช่องนี้ในดีไซน์/DTO จริง

**Assumptions**

- รายชื่ออู่ (vendor list) เป็นข้อมูลที่มีอยู่แล้วในระบบ ไม่ใช่กรอกใหม่ทุกครั้งที่สร้าง PO
- เลขไมล์ที่แสดงตอนเลือกรถเข้า PO เป็นค่าสด (live) จาก `vms_mas_vehicle.odometer` ไม่ใช่ snapshot

**สิ่งที่ยังไม่ครบ — ต้องไปหาอะไรมาเพิ่ม**

- [ ] ยืนยัน Priority (Must/Should/Could) กับ PO — ไม่มีแหล่งอ้างอิง
- [ ] ยืนยันงวดส่งมอบ/JO ที่ผูกกับฟีเจอร์นี้
- [ ] เคาะว่า PO หนึ่งใบมีได้แค่ศูนย์บริการ/อู่เดียว หรือมากกว่า 1 แห่งได้ (ลูกค้าฝากคำถามนี้ไว้ในชีตเอง)

- [ ] เคาะว่าต้องเลือกรถอย่างน้อย 1 คันก่อนบันทึก PO ได้ไหม
- [ ] เคาะว่าเปลี่ยนอู่ได้ไหมเมื่อมีรถนัดเข้าอู่แล้ว (กระทบข้อมูลที่ prefill ไปหน้านัดหมายแล้ว)
- [ ] เคาะว่านำรถออกจาก PO ได้ไหมถ้างานรายคันเริ่มไปแล้ว และข้อมูลงานของคันนั้นไปไหน
- [ ] เคาะว่าลบ PO ที่มีรถกำลังซ่อมอยู่ได้ไหม และงานรายคัน/ความคืบหน้าถูกลบทิ้งหรือเก็บประวัติ
- [ ] เคาะว่าลบ PO ควรส่ง notification N1 ถึงหน่วยงานเจ้าของรถด้วยไหม (ปัจจุบันไม่มี)
- [ ] ยืนยันว่าต้องเก็บ audit log การแก้ไข/ลบ PO ไหม (ยังไม่มีแหล่งยืนยันแยกจากกรณีแผน)

**ข้อเสนอปิดช่องโหว่ (เสนอโดย senior BA + senior dev ร่วมกัน — เป็นข้อเสนอให้ทีมพิจารณา ไม่ใช่ข้อยืนยันจากเอกสาร/บอร์ดใดๆ หมายเหตุ: บอร์ด Refinement 29 oct 2026 ไม่มีจอของ Scenario 4-6 เลย จึงไม่มีข้อมูลใหม่มาช่วยปิดช่องโหว่กลุ่มนี้ ข้อเสนอทั้งหมดด้านล่างอิงจาก pattern ที่ใช้ในส่วนอื่นของเอกสารนี้และ schema จริงที่ implement แล้วเท่านั้น)**

1. Priority → **Must** เหตุผล: เป็นขั้นต่อจากแผนทันที ไม่มี PO ก็เริ่มงานรายคัน (นัดหมาย/ตรวจรับ/ติดตาม/ปิดงาน) ไม่ได้เลย
2. งวดส่งมอบ/JO → JO เดียวกับทั้งชุด US-OH-01 ถึง 08
3. PO 1 ใบ 1 อู่หรือหลายอู่ → **1:1 ต่อไปก่อน** ตาม schema ปัจจุบันที่ implement แล้วจริง เหตุผล: ถ้าต้องการหลายอู่ให้สร้าง PO แยกใบแทน ง่ายกว่าแก้ schema ที่ทำงานอยู่แล้ว และยังคงความชัดเจนของ "1 PO = 1 อู่รับผิดชอบ" ที่ใช้เป็นหลักฐานตรวจรับ/จ่ายเงินได้ตรงไปตรงมา
4. ช่องมูลค่า PO (บาท) → **ไม่ต้องเพิ่ม** เหตุผล: งบคุมอยู่ที่ระดับแผนแล้ว (วงเงินอนุมัติของแผน) การเพิ่มช่องนี้ซ้ำซ้อนและไม่มีรองรับใน DTO จริง ถ้าต้องการเทียบงบใช้จริงให้สรุปจากอะไหล่ที่บันทึกตอนปิดงาน (US-OH-08) แทน
5. รถซ้ำ PO อื่น → **ห้าม** validate ที่ backend ตอนเลือกรถ ไม่ให้เลือกคันที่อยู่ใน PO อื่นที่ยังไม่ปิดงานอยู่แล้ว เหตุผล: ป้องกันรถคันเดียวมี 2 งานซ่อมพร้อมกันซึ่งขัดกับความเป็นจริง (รถอยู่ที่เดียวได้ที่เดียว)
6. เกณฑ์รถที่เลือกได้ → แสดงรถทุกคันที่ยังไม่อยู่ใน PO อื่นที่ active ไม่กรองตามอายุ เหตุผล: Overhaul อาจทำกับรถอายุน้อยได้เหมือนกันถ้ามีเหตุจำเป็น ไม่ควรผูกกับเกณฑ์อายุที่ใช้ตัดสินใจจำหน่ายทรัพย์สิน (เป็นคนละ flow คนละวัตถุประสงค์)
7. บังคับเลือกรถอย่างน้อย 1 คัน → **บังคับ** ปุ่มบันทึก disable จนกว่าจะเลือกอย่างน้อย 1 คัน เหตุผล: PO ที่ไม่มีรถเลยไม่มีประโยชน์ สร้างงานเปล่าในระบบ
8. เปลี่ยนอู่ได้ไหมเมื่อมีรถนัดแล้ว → **ไม่ให้เปลี่ยน** หลังมีนัดหมายแล้ว ต้องลบนัดหมายก่อนถึงจะแก้ไขอู่ได้ เหตุผล: ป้องกันข้อมูลที่ prefill ไปหน้านัดหมาย (ที่อยู่/เบอร์โทรอู่) ไม่ตรงกับอู่ใหม่
9. นำรถออกจาก PO ได้ไหมถ้างานเริ่มแล้ว → **ไม่ให้เอาออก** ถ้างานรายคันเริ่มเกินขั้นที่ 1 (นัดหมาย) แล้ว ต้องลบทั้ง PO หรือปล่อยให้ซ่อมจบ flow ไปก่อน เหตุผล: ป้องกันข้อมูลงานลอยไม่มีเจ้าของ
10. ลบ PO ที่มีรถกำลังซ่อม → **ไม่อนุญาต** ถ้ามีรถคันใดในนั้นสถานะไม่ใช่ "รอนัดหมายเข้าอู่" (ขั้นที่ 1) แล้ว เหตุผล: ป้องกันข้อมูลงานที่อยู่ระหว่างซ่อมหายไป ถ้าต้องการยกเลิกงานที่เริ่มไปแล้วควรมี flow "ยกเลิกงาน" แยกต่างหาก ไม่ใช่ลบ PO ตรงๆ
11. ลบ PO ส่ง N1 ไหม → **ส่ง** ใช้ template เดียวกับตอนเพิ่มรถแต่เปลี่ยนข้อความเป็น "รถ [ทะเบียน] ถูกถอดออกจากแผน Overhaul [ชื่อแผน]" เหตุผล: ความสมมาตรกับตอนสร้าง/แก้ไข ไม่ให้หน่วยงานงงว่ารถหายไปไหน
12. audit log การแก้ไข/ลบ PO → **ไม่เก็บ** เหตุผล: เพื่อความสม่ำเสมอของนโยบายกับแผน (BR-06 ของ US-OH-01) เป็นงานภายใน กบค. ระดับเดียวกัน

4. ช่องแนบรูป/ไฟล์ → ไม่ต้องมีในเฟสแรก เหตุผล: จอจริงล่าสุดทั้งสองรอบ (21 ต.ค. และบอร์ด Refinement 29 oct 2026) ไม่มีช่องนี้ตรงกัน ถือเป็นสัญญาณที่สม่ำเสมอว่าทีมตัดออกแล้ว เพิ่มทีหลังได้ถ้าจำเป็นจริง
5. modal ยืนยันตอนกด "ซ่อมสำเร็จ" → **ควรมี** เหตุผล: BR-03 ระบุว่าเป็นจุดปิดถาวร (แก้ไขไม่ได้อีก) เอกสารนี้ใช้ modal ยืนยันกับทุกจุดปิดถาวรแบบเดียวกันอยู่แล้ว (ลบแผน ลบ PO) ควรสม่ำเสมอกัน
6. แก้ไขได้ทุกรายการหรือเฉพาะล่าสุด / แก้หลัง "ซ่อมสำเร็จ" ได้ไหม → แก้ไขได้ทุกรายการ **ก่อน** กด "ซ่อมสำเร็จ" เท่านั้น หลังกดแล้วล็อกทั้งหมดแก้ไม่ได้อีกเลย เหตุผล: ตรงกับ BR-03 ที่ระบุไว้แล้วว่า "ย้อนมาดูได้แต่แก้ไขไม่ได้อีก" ไม่ได้บอกว่าเฉพาะรายการล่าสุด จึงตีความว่าทุกรายการแก้ได้เท่ากันก่อนปิด
7. notification ความคืบหน้ารายครั้ง → **ไม่ส่ง** เหตุผล: ลด noise ให้หน่วยงาน เอกสารนี้ออกแบบให้หน่วยงานได้ notification เฉพาะ milestone สำคัญ (N5 ตรวจรับ, N6 Safety ผ่าน, N10 ปิดงาน) การแจ้งทุกความคืบหน้าย่อยจะถี่เกินจำเป็นและไม่ตรงกับ pattern ที่ใช้ทั้งเอกสาร
8. API route + migrate ตาราง → ใช้ชื่อ draft ที่เสนอไว้แล้ว `vms_trn_overhaul_progress_log` เป็นจุดเริ่ม เพราะเป็น gap เดียวที่ยังไม่มีแม้แต่ draft migration เลย ควรเร่งคุยกับทีม backend ก่อน scenario อื่นเนื่องจากเสี่ยงบล็อก sprint
9. error handling → ใช้ pattern เดียวกับทุก scenario อื่นในเอกสารนี้ (อยู่หน้าเดิม ค่าที่กรอกคงอยู่ พร้อม toast error code จาก server) ไม่ต้องคิดรูปแบบใหม่
10. audit log แยกว่าใครแก้ไข/ลบ → **ไม่เก็บ** เหตุผล: สอดคล้องกับนโยบายรวมที่ยืนยันแล้วใน BR-06 ของ US-OH-01 ("ไม่เก็บทั้งคู่ ใครอยากทำไรก็ทำ") เป็นงานภายใน กบค. ระดับเดียวกัน ควรใช้นโยบายเดียวกันทั้งเอกสาร
11. ปุ่ม "ข้าม" ที่พบใหม่ → **ไม่เสนอความหมาย** เพราะถ้ากด "ข้าม" ได้ทั้งที่ยังไม่มีความคืบหน้าเลยจะขัดกับ BR-04 ที่ยืนยันแล้วตรงๆ (ห้ามไปขั้นที่ 4 โดยไม่มีความคืบหน้า) ความเสี่ยงสูงถ้าเดาผิด ต้องถามทีมออกแบบโดยตรงก่อนเขียนโค้ด

⚠️ **ยังไม่เคาะ (toast ข้อความปิดงาน + ปุ่ม "ข้าม" ใหม่)** — toast ในบอร์ด Refinement 29 oct 2026 แสดงข้อความสั้นกว่าที่เอกสารนี้เคยระบุ คือ "ปิดงานสำเร็จ" ไม่มีตัวแปร `{หมายเลข PO}` แทรก เหมือนรูปแบบเดียวกับ toast สร้างแผนของ US-OH-01 — อาจเป็นแค่ mockup ยังไม่ผูกตัวแปรจริง ยังไม่เคาะว่าอันไหนถูก · นอกจากนี้พบปุ่ม "ข้าม" ใหม่ในเฟรมนี้เหมือนที่พบในหน้ารายละเอียดแผน (US-OH-01 AC-09/AC-10) และหน้าติดตามงาน (US-OH-05) — ดูเหมือนเป็น pattern UI ที่ใช้ซ้ำหลายจุด แต่ไม่มีคำอธิบายว่าข้ามแล้วไปไหน/ผลกระทบอะไร ยังไม่เพิ่มเข้า AC
