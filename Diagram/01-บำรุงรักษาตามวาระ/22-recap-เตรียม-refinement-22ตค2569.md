## ภาพรวม Journey Map (จากชิ้นลอยบนเฟรม ไม่ได้อยู่ใน section ไหน)

**เส้นทางหน้าจอหลัก:**

```
start → หน้า Overhaul Management (list)
      → กด "ดูรายละเอียด" → หน้ารายละเอียดแผน
      → กด "ดูรายละเอียด รถ" → หน้ารายละเอียดรถ
      → หน้างาน Overhaul (6 ขั้น ต่อรถ 1 คัน):
          Step 1  นัดหมาย (default)
          Step 2  ตรวจรับรถ — ข้อมูลยานพหนะ / รายการเอกสารรับรถ / ลงนามการรับมอบรถ / รายละเอียดการตรวจสภาพก่อนซ่อม (Action: Next / Back)
          Step 3  ติดตามงานซ่อม — ความคืบหน้า / วันที่, เวลา (Action: Next / Back)
          Step 4  ตรวจสอบ Safety Inspection — เอกสาร

          Step 6  ปิดงาน Overhaul
```

6 ขั้นนี้คือสเตปเปอร์ที่โผล่ซ้ำในทุก section ของ Scenario 7-14 (ในรูป TABLE_CELL ชื่อ "นัดเอารถเข้าอู่ / ตรวจรับรถ / ติดตามงานซ่อม / ตรวจสภาพ / นัดรับรถ / ปิดงาน")

**Toast อื่นที่ไม่ผูกกับ status (error/edge case จากแท็บ OH-Toast):**
- บันทึกไม่สำเร็จ (ทุกฟอร์ม) → ถ้าไม่รู้ error type ให้โชว์ General Error พร้อม HTTP status code เช่น "500 Internal Server Error" ตรงๆ
- เปิดแก้ไขแผน/PO ที่ถูกลบไปแล้ว → "ไม่พบแผน {เลขแผน}" / "ไม่พบแผน"
- นำเข้าไฟล์อะไหล่ผิดรูปแบบ → ขึ้นเป็น validation message ไม่ใช่ toast ทั่วไป
- ลบแผน/ลบ PO ไม่สำเร็จ — ทีมเขียนโน้ตไว้ว่า "ทำเป็น Soft Delete ไม่น่าจะมีเคสนี้" (ยังนึกไม่ออกว่าจะเกิดจากอะไร — ถ้าใครในที่ประชุมนึกเคสออก ควรเติม)

## Scenario 1-3 — จัดการแผน Overhaul (List / Create / Detail / Edit / Delete Plan)

### มุม BA

- **ฟีเจอร์**: วางแผนงาน Overhaul ล่วงหน้าเป็นรายปีงบประมาณ ผูกกับงบ (WBS) ที่อนุมัติไว้แล้ว
- **คุณค่าทางธุรกิจ**: ป้องกันการเริ่มงาน Overhaul โดยไม่มีงบรองรับ หรือลืมติดตามว่าใช้งบไปแล้วเท่าไหร่ต่อแผน — เป็นจุดตั้งต้นของทั้งวงจรงาน (ไม่มีแผนก็เปิด PO/นัดหมาย/ตรวจรับรถต่อไม่ได้)
- **ใครใช้**: กบค. (สร้าง/แก้ไข/ลบ) — หน่วยงานเจ้าของรถไม่เกี่ยวกับขั้นนี้
- **Acceptance criteria (มุมธุรกิจ)**:
  - ต้องกรอกครบทุกฟิลด์บังคับก่อนบันทึกได้ ยกเว้น "อื่นๆ (ถ้ามี)"
  - เลือกปีงบประมาณได้ตั้งแต่ปีปัจจุบันถึง +10 ปี
  - ต้องแนบ "หนังสืออนุมัติหลักการ" และ "เอกสารอนุมัติงบ" ก่อนบันทึกแผนได้เสมอ (เอกสารอื่นไม่บังคับ)
  - แก้ไข/ลบแผนต้องมีหน้ายืนยันแยกก่อนทุกครั้ง กันกดพลาด
  - ปุ่ม "บันทึก" ต้อง disable จนกว่าจะกรอกครบตามเงื่อนไขข้างต้น

## Scenario 12 — [PEA-1.24.5][SP07] Check Safety (upload เอกสารความปลอดภัย)

- **คุณค่าทางธุรกิจ**: ยืนยันว่ารถผ่านมาตรฐานความปลอดภัยก่อนกลับไปใช้งานจริง ลดความเสี่ยงอุบัติเหตุหลังรับรถคืน และเป็นหลักฐานตรวจสอบย้อนหลังได้

## Scenario 13 — Appointment (นัดหมายรับรถคืน)

### มุม BA

- **ฟีเจอร์**: นัดหมายวันรับรถคืนจากอู่ กลับไปใช้งาน — เหมือน Scenario 7 แต่กลับทาง
- **คุณค่าทางธุรกิจ**: หน่วยงานเจ้าของรถรู้ล่วงหน้าว่าจะได้รถคืนวันไหน วางแผนใช้งานรถต่อได้
- **ใครใช้**: กบค. (สร้างนัดหมาย) · หน่วยงานเจ้าของรถ (ตอบรับ/ปฏิเสธ)
- **Acceptance criteria (มุมธุรกิจ)**: เดียวกับ Scenario 7 ทุกข้อ (reuse flow เดิมทั้งหมด)
- **⚠️ ไม่มีเลข sprint ระบุบนบอร์ด และไม่มี sticky FE/BE ใหม่ติดเลย** — ต้องเคาะว่าจะทำพร้อม Scenario 7 ในรอบเดียวกัน (เพราะ reuse flow/field เหมือนกันหมด) หรือจะแยกเป็น sprint ถัดไป **อัปเดตจากชีต**: ถึงจะไม่มี sticky FE/BE แต่ status/toast/สิทธิ์ของขั้นนี้ถูกออกแบบไว้ครบแล้วในชีต (ดูมุม Dev) แปลว่า BA/flow ไม่ได้ขาดจริง — แค่ยังไม่ถูกแตก task FE/BE ให้ dev เท่านั้น

### มุม Dev

ฟอร์มเดียวกับ Scenario 7 ทุกฟิลด์: ช่วงวันนำรถคืน · ที่อยู่ · ชื่ออู่ · เบอร์อู่ · ผู้ประสานงาน (กบค.) · เบอร์โทรผู้ประสานงาน (กบค.) · ปุ่มยืนยันนัดหมาย — สถานะ "รอหน่วยงานเจ้าของรถตอบกลับ" + ปุ่มแก้ไขนัดหมาย เหมือน Scenario 7 เป๊ะ

**ไม่มี sticky ใหม่ติดใน section นี้** — ดูเหมือนตั้งใจให้ reuse flow เดียวกับ Scenario 7 ทั้งหมด ไม่ต้องคุยซ้ำ

**Status/Toast (จากชีต) — มีครบ แม้ FigJam จะไม่มี sticky:** ยืนยันนัดหมาย → `รอหน่วยงานตอบรับนัดรับรถ` → toast *"นัดหมาย {ข้อมูลสำคัญ} สำเร็จ"* · หน่วยงานตอบรับ → **`รอปิดงาน`** (status final "หน่วยงานตอบรับรถแล้ว") · หน่วยงานปฏิเสธ → `หน่วยงานปฏิเสธนัดรับรถ` — โครง status/toast เหมือน Scenario 7 เป๊ะตามที่คาดไว้ ต่างกันแค่ปลายทางหลังตอบรับ (Scenario 7 ไปตรวจรับรถ, Scenario 13 ไปปิดงานได้เลย)

## Scenario 14 — ปิดงาน (Closing work)

### มุม BA

- **ฟีเจอร์**: บันทึกรายการค่าใช้จ่ายจริงที่เกิดขึ้นระหว่าง Overhaul แล้วปิดงาน
- **คุณค่าทางธุรกิจ**: เทียบค่าใช้จ่ายจริงกับงบที่อนุมัติไว้ตอนสร้างแผน (Scenario 1) ปิดวงจรงานอย่างเป็นทางการ มีหลักฐานใบสำคัญจ่ายอ้างอิงได้
- **ใครใช้**: กบค.
- **Acceptance criteria (มุมธุรกิจ)**: **(จากชีต — ตอบคำถามที่ค้างไว้แล้ว)** ต้องมีอะไหล่/รายการอย่างน้อย 1 รายการก่อนกดปิดงานได้ (ยืนยันตรงจากชีต ไม่ใช่การเดา) · ที่ยังไม่ชัด: "เลขใบสำคัญจ่ายต้องตรวจสอบกับระบบบัญชีไหม หรือพิมพ์เองได้เลย" — ชีตไม่ได้ตอบจุดนี้ ยังต้องถามในที่ประชุม
- **⚠️ ไม่มีเลข sprint ระบุบนบอร์ด** — ต่างจาก prototype เก่า (`app/src`) ที่เคยรวมเรื่องประกัน/Safety ไว้ที่ขั้นปิดงานด้วย ตอนนี้บอร์ดแยก Safety ออกไปเป็น Scenario 12 แล้ว เหลือ Scenario 14 ไว้แค่เรื่องค่าใช้จ่าย — ควรยืนยันในที่ประชุมว่าเข้าใจตรงกัน (รายละเอียดการเทียบกับ prototype เก่าอยู่ใน `21-overhaul-full-audit.md`) **อัปเดตจากชีต**: แม้ไม่มี sticky FE/BE แต่ status/toast ของขั้นนี้ถูกออกแบบไว้ครบแล้ว (ดูมุม Dev) เหมือนกรณี Scenario 13

### มุม Dev

**เนื้อหา:** รายการจัดซื้อ — ตาราง "รายการ / ค่าใช้จ่าย (Text number) / ใบสำคัญจ่ายเลขที่ (Free text)" · ปุ่ม "+ เพิ่มรายการ" · ปุ่ม "ปิดงาน"

**ไม่มี sticky `[FE]`/`[BE]` ติดอยู่ใน scenario นี้เลย** เหมือน Scenario 8

**Status/Toast (จากชีต):** ระบุอะไหล่ → status `รอปิดงาน` (status final "อยู่ระหว่างปิดงาน") → นำเข้าไฟล์อะไหล่สำเร็จ → toast *"นำเข้าไฟล์ {ชื่อไฟล์} สำเร็จ"* (ผิดรูปแบบ → ขึ้น validation ไม่ใช่ toast) · กด "ปิดงาน" (ต้องมีอะไหล่ ≥1 รายการ) → status **`ปิดงานแล้ว`** (final "เสร็จสิ้น") → toast *"ปิดงาน {ข้อมูลสำคัญ} เรียบร้อยแล้ว"* + notification → หลังจากนี้ทุกฝ่าย **ดูได้อย่างเดียว แก้ไขไม่ได้อีก**
