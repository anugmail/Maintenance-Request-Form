# Overhaul Dashboard: มุมมองผู้บริหาร — เรียง Business Value สูงสุดก่อน + เช็คกับข้อมูลจริงใน maintain-d-be (24 ต.ค. 2569)

ต่อยอดจาก `27-overhaul-dashboard-business-value-poc.md` — รอบนี้เรียงใหม่จากมุม**ผู้บริหารตัดสินใจ** (ไม่ใช่เรียงตามความง่ายในการสร้าง) แล้วเช็คว่าอันไหนทำได้จาก**ข้อมูลที่อยู่ใน `maintain-d-be` เพียงรีโปเดียว** (รีโป Overhaul ที่ทีมนี้ดูแลเอง) กับอันไหนต้องง้อข้อมูลข้าม repo ไปที่ `vms-plus-main-be` (คนละทีมดูแล)

ป้ายสถานะ: **✅ maintain-d-be ล้วน พร้อมทำวันนี้** · **🟡 maintain-d-be ล้วน แต่ข้อมูลยังหยาบ** (ใช้วันนัดแทนวันจริง) · **🔗 ต้องข้าม repo** (ง้อ `vms-plus-main-be` อย่างน้อย 1 field) · **❌ ไม่มีตารางรองรับเลย**

|---|---|---|---|
| **1** | **A1+A2 — ค่า Overhaul สะสมเทียบราคารถ/ราคาซื้อใหม่ ("คุ้มมั้ย")** | คำถามหลักที่ขับเคลื่อนทั้งฟีเจอร์นี้ — ตอบได้ตรงว่าเงินที่ลงไปกับ Overhaul คุ้มกว่าซื้อรถใหม่ไหม ใช้ตัดสินใจระดับงบประมาณปีถัดไปได้เลย | **🔗 ต้องข้าม repo** — ราคารถ (`vehicle_price`) อยู่ใน `vms-plus-main-be` ไม่ใช่ `maintain-d-be` และฝั่ง `maintain-d-be` เองก็ยังไม่มีคอลัมน์ "มูลค่า PO ต่อคัน" — **จึงทำไม่ได้แม้จะใช้ maintain-d-be ล้วนๆ** ต้องเพิ่ม field ใน `vms_trn_purchase_order` ก่อน แล้วค่อย join ข้าม repo |

| **3** | **B1+B3 — เวลาเฉลี่ย/อัตรากลับมาซ่อมซ้ำหลัง Overhaul (90/180 วัน)** | วัดว่า "เงินที่จ่ายไปกับ Overhaul ได้ผลจริงไหม" ไม่ใช่แค่จ่ายแล้วจบ — ถ้าซ่อมซ้ำเร็วมาก แปลว่าคุณภาพงาน Overhaul มีปัญหา ไม่ใช่แค่ปัญหารถเก่า | **🟡 maintain-d-be ล้วน แต่ข้อมูลยังหยาบ** — `vms_trn_overhaul_po_vehicle_appointment` (วันคืนรถ) + `vms_trn_repair_job.repair_job_date` อยู่ใน repo เดียวกันหมด ทำได้เลยวันนี้ แค่ใช้ "วันนัด" แทน "วันจริงที่ยืนยันแล้ว" (แม่นยำน้อยกว่าที่ควร) |

| **5** | **C1 — ค่าใช้จ่าย Overhaul รวมต่อปีงบ เทียบปีก่อนหน้า** | คำถามงบประมาณพื้นฐานที่สุดที่ผู้บริหารถามทุกปี — งบปีนี้บานขึ้นจากปีที่แล้วไหม | **✅ maintain-d-be ล้วน พร้อมทำวันนี้** — `vms_trn_overhaul_job.approved_budget` + `fiscal_year` ครบในตารางเดียว |
| **6** | **D2 — เวลาเฉลี่ยที่รถ "อยู่อู่" ต่ออู่ (lead time)** | ประเมินประสิทธิภาพอู่เชิงปฏิบัติการ (เสริม D1) — อู่ไหนรับงานเร็ว/ช้ากว่าที่นัดไว้ | **✅ maintain-d-be ล้วน พร้อมทำวันนี้** — วันนัดเข้า/คืน + ชื่ออู่ อยู่ใน repo เดียวกันหมด (ความแม่นยำมีข้อจำกัดเดียวกับข้อ 3 เพราะใช้วันนัด) |

## สรุปสำหรับผู้บริหาร

**ถ้าต้องเลือกสร้างแค่ 3 อันดับแรกที่ทำได้จริงวันนี้ด้วยข้อมูลใน `maintain-d-be` อย่างเดียว** (ไม่ต้องรอ field ใหม่ ไม่ต้องข้าม repo):

1. **C3 — สัดส่วนรถ Overhaul ซ้ำ** (อันดับ business value #2 + ✅ พร้อมสร้างวันนี้) — ใกล้เคียงคำถาม "คุ้มมั้ย" ที่สุดเท่าที่ทำได้ตอนนี้โดยไม่ต้องรอราคารถ
2. **B1+B3 — เวลา/อัตรากลับมาซ่อมซ้ำหลัง Overhaul** (อันดับ #3 + 🟡 ทำได้วันนี้ ข้อมูลหยาบนิดหน่อย) — ตอบคำถามที่คุณถามตรงๆ ("ใช้ได้นานแค่ไหนถึงจะซ่อมอีก")
3. **C1 — งบ Overhaul ต่อปีเทียบปีก่อน** (อันดับ #5 + ✅ พร้อมสร้างวันนี้) — คำถามงบประมาณพื้นฐานที่ผู้บริหารถามทุกปี

### เพิ่มตามที่ขอ 24 ต.ค. 2569 (ค่ำ): C2 — "รถรุ่นไหน ยี่ห้ออะไร ทำ Overhaul เยอะสุด"

เจ้าของงานยืนยันอยากได้ตัวนี้เพิ่มเป็นข้อ 4 ของชุดที่จะสร้าง (เดิมอยู่อันดับ #7 ของผังความสำคัญ แต่ตอนนี้ถูกยกเข้าชุด priority แล้ว)

- **ต้องการชื่อยี่ห้อ/รุ่นรถจริง ไม่ใช่แค่นับจำนวนครั้ง** ⇒ ต้อง join ข้าม repo ไป `vms_mas_vehicle` ที่ `vms-plus-main-be` จริง — **แต่เป็นงานเบากว่าที่คิด**: `vms_mas_vehicle` มีคอลัมน์ `VehicleBrandName` และ `VehicleModelName` (`models/vehicle_model.go:159,161`) เป็น**ชื่อสำเร็จรูปอยู่แล้ว** ไม่ต้องไป join ตารางอ้างอิงยี่ห้อ/รุ่นอีกชั้น — join ครั้งเดียวด้วย `mas_vehicle_id`/`MasVehicleUID` ก็พอ ไม่ใช่การเชื่อมระบบใหม่แบบ A1 ที่ต้องเพิ่ม field ที่ไม่มีอยู่เลย
- สูตร: `COUNT(vms_trn_po_vehicle) GROUP BY mas_vehicle_id` (ฝั่ง maintain-d-be) → join เอาชื่อยี่ห้อ/รุ่นจาก `vms_mas_vehicle` (ฝั่ง vms-plus-main-be) มาแปะตอนแสดงผล
- สถานะ: **🔗 ต้องข้าม repo แต่ทำได้ทันที** (field ที่ต้องการมีอยู่แล้วทั้งสองฝั่ง ไม่ต้องรอเพิ่ม migration ใหม่) — ต่างจาก A1 ที่ยังต้องเพิ่ม field ที่ไม่มีอยู่เลยก่อน

**ชุด priority ล่าสุด (4 ตัว) ที่ควรผลักดันก่อน**: C3 → B1+B3 → C1 → **C2 (ยี่ห้อ/รุ่นที่ Overhaul บ่อยสุด)**

**ตัวที่ business value สูงสุด (A1+A2 "คุ้มมั้ยกับซื้อใหม่") ยังคงเป็นตัวเดียวที่ทำไม่ได้แม้จะยอมข้าม repo** — เพราะไม่ใช่แค่ต้อง join แต่ต้อง**เพิ่ม field ใหม่**ที่ไม่มีอยู่เลย ("มูลค่า PO ต่อคัน" ใน `maintain-d-be`) ก่อนถึงจะ join เอา `vehicle_price` จาก `vms-plus-main-be` ได้ — นี่คือช่องว่างสำคัญที่สุดถ้าอยากให้ dashboard ตอบคำถามหลักของผู้บริหารได้แบบเต็มรูปแบบ ไม่ใช่แค่สัญญาณหยาบๆ

## ยังไม่เคาะ

- ตัวเลขทั้งหมดเช็คแค่ "มีคอลัมน์ในสคีมาไหม" ไม่ได้ยืนยันว่าแถวข้อมูลถูกกรอกครบกี่ % ต้องให้ทีม backend/DBA ยืนยันอีกชั้น
- C2: ยังไม่เช็คว่า `VehicleBrandName`/`VehicleModelName` ของ `vms_mas_vehicle` ถูกกรอกครบทุกคันจริงไหม หรือมีบางคันเป็นค่าว่าง
