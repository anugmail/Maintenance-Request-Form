## สรุปสิ่งที่เจอใหม่ ไม่มีใน 21/22 (อ่านก่อน)

1. **มีตาราง schema ร่างสำหรับ Scenario 8/9-11/14 อยู่จริงบนบอร์ด** — เอกสาร 21 สรุปว่า Scenario 8-14 "ไม่มีแม้แต่ draft migration" แต่บนบอร์ดมีตารางร่างชื่อ `vms_trn_overhaul_po_vehicle` (ลายเซ็น 2 ฝ่าย), `vms_trn_overhaul_inspection_form_items` (checklist), `vms_trn_overhaul_progress_log` (follow-up), `senario14` (รายการ/ค่าใช้จ่าย/ใบสำคัญจ่าย), `vms_mas_overhaul_po_vehicle_status` (status lookup) — เป็น**ร่างบนบอร์ดเท่านั้น ยังไม่ได้ migrate จริงในโค้ด** (ไม่ขัดกับเอกสาร 21 ที่เช็คจากโค้ดจริง) แต่มีประโยชน์มากสำหรับ propose schema ตอนพัฒนาจริง ไม่ต้องเริ่มจากศูนย์
2. **คอนเฟิร์มคำถามค้างของ AC-S2 แล้ว**: "แก้ไข/ลบ เก็บข้อมูลเก่าไว้ไหม" → **ไม่เก็บทั้งคู่** ("ไม่เก็บทั้งคู่ ใครอยากทำไรก็ทำ") — ไม่มี audit log
3. **ยืนยัน cost_type มี column จริงแต่ไม่ใช้** — ตาราง `vms_trn_overhaul_job` บนบอร์ดมีคอลัมน์ `cost_type varchar` พร้อมโน้ต "ไม่ได้ใช้เพราะเป็น wbs ทั้งหมด" และ `purchase_order int` โน้ต "ตัดออกไม่ต้องเก็บ" — ตรงกับที่เอกสาร 21 สรุปไว้เป๊ะ (ศูนย์ต้นทุน = ปิดแล้ว ใช้ WBS)
4. **เจอ warranty-notification schedule ที่ไม่มีในเอกสารไหนเลย** — ตาราง Action/Status/Notification บนบอร์ดระบุว่า หลังรถ "พร้อมใช้งาน" ระบบจะส่งแจ้งเตือนวันสิ้นสุดประกัน **ล่วงหน้า 1 เดือน 1 ครั้ง + 15 วัน 1 ครั้ง** ไปที่เจ้าของรถและ กรย. — ไม่เคยถูกพูดถึงในไฟล์ 15/18/21/22 เลย ต้องเคาะว่ายังอยู่ใน scope ไหม
5. **เจอไอเดีย "ประเมินความพึงพอใจ" ที่ไม่มีใน scope ปัจจุบัน** — sticky แยก 2 อัน พูดถึงหน่วยงานหน้างานประเมินอู่/กบค. และกบค.ประเมินอู่ — ดูเป็นไอเดียหลวมๆยังไม่ตกผลึกเป็น scenario ต้องถามว่าทำหรือไม่ทำ
6. **ตรรกะสิทธิ์ "หน่วยงาน" ที่เป็นรูปธรรมกว่าที่เคยสรุปไว้** — เจอ dept_sap/dept_upper matching logic จริง: `if database.dept_upper == REQUEST.dept_sap then can edit` และตัวอย่างข้อมูลจริงจาก HR API (dept_sap 9121, dept_upper 8507 ฯลฯ) — "หน่วยงาน" ในบริบทนี้ถูกนิยามเป็น "ลูกน้องของ กบค." ผ่าน dropdown select ไม่ใช่สิทธิ์แบบ role ทั่วไป เอกสาร 21/22 ไม่เคยพูดถึงกลไกนี้เลย
7. **พบ edge case ที่ยอมรับว่ายังไม่รองรับตรงๆ**: "ยังไม่รองรับ exeptional case เช่น user ลบแผนในขณะที่มีคนแก้ไขอยู่" (ไม่มี optimistic locking) — ควรใส่ใน "ยังไม่เคาะ" ของ AC-S2/S3
8. **ชัดเจนเรื่อง navigation หลังบันทึก/ยกเลิก ของฟอร์มแก้ไข**: ยืนยันแก้ไขเสร็จ หรือกดยกเลิก จะ "กลับไปหน้าที่เข้ามา" (มาจาก list ก็กลับ list, มาจาก detail ก็กลับ detail) ไม่ใช่กลับไปหน้ารายละเอียดเสมอแบบที่ไฟล์ 15 สรุปไว้ — ต้องปรับ AC-S2
9. **เมนู 3 จุดบนแถว PO (ไม่ใช่แถวแผน) ยืนยันว่าเป็นเมนูจริง** — sticky "แสดง 3 เมนู ดูรายละเอียด แก้ไข ลบ" ผูกกับแถว PO ในหน้ารายละเอียดแผน — ต่างจากแถวแผนในหน้า list ที่ไฟล์ 18 ยืนยันว่าเป็นไอคอน 3 ปุ่มแยก ไม่ใช่เมนู — สองหน้าใช้ pattern คนละแบบกันจริง ไม่ใช่ความสับสนจากชื่อเฟรม
10. **อัปโหลดรับ .png ด้วย** (ไม่ใช่แค่ PDF/JPG) — ตรงกับที่เห็นในจอจริง (B.1) แต่ไม่เคยถูกระบุชัดในเอกสารข้อความ
11. **step ย้อนกลับ (back) ของ stepper ไม่ขึ้น modal เตือน** แต่ modal เตือนจะขึ้นเฉพาะตอนกด "ย้อนกลับ"/sidebar/breadcrumb เท่านั้น (ชัดกว่าที่เคยสรุปไว้ว่า "มี modal ยืนยันการออก" แบบรวมๆ)
12. **Vendor data ยืนยัน endpoint จริงอีกครั้งพร้อม curl ตัวอย่างสมบูรณ์** (ตรงกับเอกสาร 21 ที่อ้าง `pea_vendor_client.go`)

## Scenario 2 — กบค. แก้ไขแผน [PEA-1.23.2]

**กำหนดให้** มีแผนอยู่แล้ว เข้าได้ 2 ทาง: (2.1) action "แก้ไข" ตรงจากหน้า list → ไปหน้าแก้ไขเลย (design เดียวกับหน้าสร้าง) หรือ (2.2) เข้าหน้ารายละเอียดก่อน แล้วกด "แก้ไข" → confirm → หน้าแก้ไข
**เมื่อ** แก้ค่าในฟอร์ม (ฟอร์มเดียวกับสร้างแผน, prefill ค่าเดิมทุกช่อง) แล้วกด "บันทึก"
**แล้ว** ขึ้น modal ยืนยันการแก้ไข → ยืนยันแล้วบันทึกสำเร็จ

### หลังบันทึก / ยกเลิก — **จุดที่ต่างจากไฟล์ 15**

- บันทึกสำเร็จ **กลับไปหน้าที่เข้ามาตอนแรก** ไม่ใช่กลับหน้ารายละเอียดเสมอ — มาจากหน้า list ก็กลับหน้า list, มาจากหน้ารายละเอียดก็กลับหน้ารายละเอียด (sticky ยืนยันตรงๆ)
- กดยกเลิกในหน้าแก้ไข ก็ใช้กฎเดียวกัน "มาทางไหนกลับทางนั้น"
- แก้ไขได้ **ทุกฟิลด์** (sticky ยืนยันซ้ำ 2 จุด: "แก้ไขได้ทุกฟิลด์")

### กันพลาด

- แก้แล้วกด "ยกเลิก"/ย้อนกลับ: modal "มั่นใจรึว่าจะย้อนกลับ"

### ข้อห้าม

(ไม่มีข้อห้ามเฉพาะเพิ่มจากบอร์ด)

### ยังไม่เคาะ / ตอบแล้ว

- **ตอบแล้ว**: "แก้ไข/ลบ ข้อมูลเก่าเก็บไว้ไหม" → **ไม่เก็บทั้งคู่** ("ใครอยากทำไรก็ทำ" — คำตอบดิบจากบอร์ด ฟังดูเหมือนทีมยังไม่ซีเรียสกับเรื่องนี้ แต่สรุปคือไม่มี audit log แน่นอน)
- **ใหม่**: ยังไม่รองรับ concurrent edit ("ยังไม่รองรับ exeptional case เช่น user ลบแผนในขณะที่มีคนแก้ไขอยู่") — ไม่มี optimistic lock / version check

## Scenario 3 — กบค. ลบแผน [PEA-1.23.3]

**กำหนดให้** มีแผนอยู่แล้ว เข้าได้ 2 ทาง (จากหน้า list หรือหน้ารายละเอียด) เหมือน S2
**เมื่อ** กด "ลบแผน" → modal "ยืนยันการลบแผน"
**แล้ว** ยืนยันแล้วลบสำเร็จ กลับหน้า list (ถ้ามาจาก list) หรือกลับ list เสมอหลังลบ (ลบแล้วรายละเอียดเดิมไม่มีอยู่แล้ว)

### ข้อห้าม

- ห้ามลบโดยไม่มี modal ยืนยัน

### ยังไม่เคาะ / ตอบแล้ว

- **ตอบแล้ว (เอกสาร 18 + บอร์ด)**: เป็น soft delete ไม่ใช่ hard delete — บอร์ดมีร่องรอยว่าเคยถกกันว่าจะ hard หรือ soft (sticky "hard delete", sticky "20 ตค 69 รอ CF ว่า hard-delete ไหม", sticky คู่ "hard delete → soft-delete") สรุปสุดท้ายคือ **soft delete** ตรงกับไฟล์ 18
- "ลบสำเร็จ มีอะไรแจ้งหรือไม่" — sticky ตอบว่า "ยังไม่มี" ซึ่งอาจหมายถึงไม่มี notification เพิ่มเติมนอกจาก toast (ไม่ใช่ไม่มี toast เลย เพราะ toast "ลบแผน Overhaul {เลขแผน} สำเร็จ" ถูกยืนยันไว้ในเอกสารอื่นแล้ว) — ควรตีความว่า "ไม่มี notification ส่งถึงคนอื่นเพิ่มเติม" ไม่ใช่ "ไม่มี toast"
- ยังไม่รองรับ exceptional case เดียวกับ S2 (concurrent edit/delete)

- วิธีเซ็น (บอร์ดบอกแค่ "เซ็นจริง มี design แล้ว" ไม่ได้บอกกลไก)

**เมื่อ** กด "ลบ" ที่รายการ → modal ยืนยัน ("ยืนยันการลบความคืบหน้า")
**แล้ว** ยืนยันแล้วรายการหายจากตาราง

### กันพลาด — กฎการลบที่ชัดกว่าที่เคยสรุปไว้

sticky ยืนยันตรงๆ: **"มี cf modal เสมอ / มีมากกว่า 1 ความคืบหน้า จะลบเฉพาะความคืบหน้านั้น / ถ้ามีแค่ 1 ความคืบหน้า จะลบ column ไปด้วย ไป default stage"**

ตีความ: ถ้าเหลือความคืบหน้าแค่ 1 รายการแล้วลบ ไม่ใช่แค่ลบรายการนั้น แต่ **ตารางทั้งคอลัมน์หายไปด้วย กลับไปเป็นสภาพว่าง (default stage)** — ตรงกับไฟล์ 15 ที่ว่า "ข้อห้าม: ห้ามลบจนเหลือ 0 รายการ" แต่จริงๆ จากบอร์อดูเหมือน**อนุญาตให้ลบจนเหลือ 0 ได้** แค่กลับไปสภาพว่างเท่านั้น (ไม่ใช่ปุ่มลบหายไปตอนเหลือ 1 รายการแบบที่ไฟล์ 15 บอก) — **นี่คือจุดขัดกันเองที่ต้องเคาะก่อนเขียน AC จริง**: ไฟล์ 15/บอร์ดส่วนอื่นบอกว่า "เหลือรายการเดียว ปุ่มลบไม่แสดง" แต่ sticky ตัวนี้บอกว่าลบได้แล้วกลับ default stage — ขัดกันเอง 2 แหล่ง

## Scenario 14 — กบค. ปิดงาน Overhaul (ไม่มีเลข ticket)

**กำหนดให้** หน่วยงานตอบรับนัดรับรถแล้ว (step 6)
**เมื่อ** กรอกรายการจัดซื้อ (รายการ/ค่าใช้จ่าย/ใบสำคัญจ่ายเลขที่) อย่างน้อย 1 รายการ แล้วกด "ปิดงาน"
**แล้ว** รถปิดงาน เมื่อรถทุกคันในทุก PO ของแผนปิดงานครบ สถานะแผนเป็น `completed` อัตโนมัติ

### ⚠️ เนื้อหาบนบอร์ดนี้ตรงกับ Figma dump (ไม่ใช่กรอกอะไหล่!) — ต่างจากที่ไฟล์ 15 (AC-S14) อ้างอิง

บอร์ด FigJam (ใหม่กว่า, ผ่านรีไฟน์เมนต์ 15 ต.ค. 2569) ของ Scenario 14 เป็น**ตารางรายการจัดซื้อ/ค่าใช้จ่าย** ล้วนๆ:

|---|---|

| ค่าใช้จ่าย | Text number |
| ใบสำคัญจ่ายเลขที่ | Free text |

ปุ่ม "+ เพิ่มรายการ" / "ปิดงาน" (disable จนกว่าจะมีรายการอย่างน้อย 1 แถว — sticky: "ปุ่ม ปิดงาน แสดงเป็น Disable เมื่อยังไม่ได้กรอกรายการจัดซื้อ / Enable เมื่อเพิ่มรายการจัดซื้ออย่างน้อย 1 รายการ")

- ล่วงหน้า 1 เดือน ส่ง 1 ครั้ง
- ล่วงหน้า 15 วัน ส่ง 1 ครั้ง
- ข้อความ: "แจ้งวันสิ้นสุดประกัน วันที่... โปรดตรวจสอบความเรียบร้อย"
- ส่งถึง: เจ้าของรถ, กรย. (ตัดคำที่ dump ไว้ไม่ครบ)

ไม่เคยถูกพูดถึงในไฟล์ 15/18/20/21/22 เลย — **ต้องเคาะว่ายังอยู่ใน scope ของ 14 scenario นี้ไหม หรือเป็นฟีเจอร์แยกที่ยังไม่ได้ ticket**

- Sticky ภาพรวม: "Permission กบค view และ edit / หน่วยงาน view"

  ```

       can edit
  end
  ```
- มีตัวอย่างข้อมูลจริงจาก HR API ทดสอบ (`dept_sap: 9121`, `dept_upper: 8507` ฯลฯ, env `HR_API_USE_MOCK=false`, `HR_API_BASE_URL=http://10.4.32.147`)
- คำถามเปิดบนบอร์ดเอง (ยังไม่มีคำตอบ): "หาลูกน้องตัวเองยังไง ถ้าเข้ามาในรูปแบบ หัว BB" และ "Q: dept_shot1-7 คือบอก level ของแผนกหรอ? ANS: (ว่าง ไม่มีคำตอบ)"

### เอกสาร — เหตุผลที่แยกตารางเอกสาร 2 ชุด (overhaul vs PO)

ข้อความอธิบายสถาปัตยกรรมตรงบนบอร์ด: แยกตาราง document เพราะ "foreign key ตรวจรหัสให้และลบตามแม่ได้ แถวไม่มีคอลัมน์ว่าง และเพิ่มแม่ชนิดใหม่โดยไม่แก้ตารางเอกสารเดิม" ข้อเสียคือ "column ซ้ำหลายตารางและถ้าต้องค้นไฟล์ของทั้งหมดแม่..." (ประโยคถูกตัดกลางคันในต้นฉบับ) — เหตุผลเชิงสถาปัตยกรรมที่ไม่เคยถูกบันทึกไว้ที่ไหนมาก่อน

### Relationship cardinality ที่ระบุไว้บนบอร์ด (ไม่เคยถูกจดที่ไหน)

- `one to many` ×3 จุด (ไม่ได้ติดป้ายว่าคู่ไหน-ไหน ต้องดูตำแหน่งบนบอร์ดจริงถ้าต้องการยืนยัน)
- `one to one` ×1 จุด
