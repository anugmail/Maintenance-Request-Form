# Feature ประวัติและปิดงาน: journey หน้า และ case สำหรับทีม dev

> ร่าง 17 พ.ย. 2569 ตามรูปแบบของ Feature แผนบำรุงรักษา (ไฟล์ 32)
> ลอกเนื้อหาจากงานเดิม (userflow ไฟล์ 14 scenario 15 ถึง 18 · จอใน `figma-export/maintainance-plugin/screens.js`) มาจัดใหม่ ไฟล์เดิมไม่ได้แก้
> ปลั๊กอิน: `figma-export/maintainance-feature-plugin/features/close.js`

## 0. กติกาของเอกสารนี้

### 0.1 ชั้นของงาน

- **Feature** ก้อนงานที่ทีม dev รับไปทำ ประกอบด้วยหลายหน้า
- **Journey** งานหนึ่งเรื่องที่ผู้ใช้ตั้งใจทำ ครอบหน้าที่เกี่ยวข้องและทางเปลี่ยนหน้า
- **หน้า** หน้าจอที่ dev ต้องสร้าง
- **case** หน้าตาแบบหนึ่งของหน้านั้น

### 0.2 ไม่สร้างหน้าซ้ำ

1. **Toast สร้างเป็นชิ้นเดียว ไม่สร้างทั้งหน้าซ้ำ** ทุก toast เป็น component Notification ของไลบรารีชิ้นเดียว มีป้ายบอกว่า **แสดงบนหน้าไหน เมื่อไหร่** ตัวอย่าง: toast "ดาวน์โหลดไฟล์ Excel แล้ว" แสดงบนหน้าต้นทุนการบำรุงรักษา เมื่อกดดาวน์โหลด Excel ไม่ต้องสร้างหน้าต้นทุนที่มี toast ขึ้นมาอีกจอ ตำแหน่งบนจอจริงคือมุมขวาบนเสมอ
2. **case ที่หน้าตาเหมือนกันสร้างครั้งเดียว** journey อื่นที่ใช้ case นั้นอ้างรหัสจอเดิม ไม่สร้างใหม่
3. **case ที่หน้าเปลี่ยนจริง ยังสร้างเต็มหน้า** เช่น ส่งประวัติแล้ว ป้ายสถานะ กล่องแจ้ง และปุ่มเปลี่ยน ต้องมีจอของสภาพนั้น แต่ toast ที่ขึ้นพร้อมกันแยกเป็นชิ้น

### 0.3 ชื่อ case มาตรฐาน

| case | ความหมาย |
|---|---|
| Default | เปิดหน้าครั้งแรก ยังไม่มีข้อมูล หรือยังไม่กรอก |
| Filled | มีข้อมูล หรือกรอกครบแล้ว |
| Interaction | ระหว่างใช้งาน เช่น เปิดรายการเลือก แผงตัวกรอง popup เมนู |
| Empty result | ค้นหาหรือกรองแล้วไม่พบ |
| Disabled | ปุ่มกดไม่ได้เพราะเงื่อนไขยังไม่ครบ |
| Error Validation Field | ช่องที่ต้องกรอกยังว่าง แสดง error ตอนออกจากช่อง |
| Confirm | หน้าต่างยืนยันก่อนทำต่อ |
| Role · Status | หน้าตาต่างกันตามบทบาทผู้ใช้ หรือสถานะของแผน |
| Toast | ชิ้นแยก ตามข้อ 0.2 |

### 0.4 รหัสจอ

## 2. Journey

แต่ละ journey มี 3 ส่วน: ทางเดิน (action แล้วไปหน้าไหน) · case ของแต่ละหน้าตามลำดับที่เดิน · toast ของ journey

### J1 บันทึกและส่งประวัติ

**ทางเดิน**

| # | อยู่หน้า | ทำอะไร | ผล | ไปหน้า |
|---|---|---|---|---|
| 1 | ประวัติงานบำรุงรักษา | ดูความคืบหน้ารายคัน | ยังไม่ครบทุกคัน ปุ่มส่งประวัติกดไม่ได้ | อยู่หน้าเดิม |
| 2 | ประวัติงานบำรุงรักษา | กดส่งประวัติให้หัวหน้าตรวจสอบ แล้วยืนยัน | สำเร็จ | อยู่หน้าเดิม สถานะรอหัวหน้าตรวจสอบ + toast H1 |
| 2.1 | ประวัติงานบำรุงรักษา | ยืนยันส่ง | ไม่สำเร็จ | **ยังไม่มีจอ** |
| 3 | ประวัติงานบำรุงรักษา | ย้อนกลับ | | หน้าที่มา |

**หน้าประวัติงานบำรุงรักษา** (4 จอ)
- Disabled ยังบำรุงรักษาไม่ครบทุกคัน กล่องแจ้งเหลือกี่คัน ปุ่มส่งประวัติกดไม่ได้ (N.1)
- Filled ครบทุกคัน ตารางประวัติงานบำรุงรักษาทั้งหมด (N.2)
- Confirm ยืนยันส่งประวัติ "ประวัติงานบำรุงรักษา {n} คันของแผน {เลขที่ MR} จะแก้ไขไม่ได้จนกว่าหัวหน้าจะตรวจเสร็จ" (N.3)
- Status ส่งแล้ว รอหัวหน้าตรวจสอบ กล่องแจ้ง ปุ่มส่งหาย (N.4) + toast H1
- Status ถูกตีกลับ แสดงเหตุผลให้แก้ **ยังไม่มีจอ**

**Toast ของ J1**

| รหัส | ข้อความ | ชนิด | แสดงบนหน้า | เมื่อ | แทนจอเดิม |
|---|---|---|---|---|---|
| H1 | ส่งประวัติงานบำรุงรักษาให้หัวหน้าตรวจสอบแล้ว | Success | ประวัติงานบำรุงรักษา | ยืนยันส่งประวัติสำเร็จ | ชิ้นใน N.4 |

### J2 ตรวจสอบประวัติ

**ทางเดิน**

| # | อยู่หน้า | ทำอะไร | ผล | ไปหน้า |
|---|---|---|---|---|
| 1 | ประวัติรอตรวจสอบ | กดแผน | | ตรวจสอบประวัติ |
| 2 | ตรวจสอบประวัติ | อนุมัติประวัติ แล้วยืนยัน | สำเร็จ | อยู่หน้าเดิม สถานะผ่านแล้ว + toast H2 |
| 2.1 | ตรวจสอบประวัติ | ตีกลับ ระบุเหตุผล แล้วกดตีกลับ | สำเร็จ | **ยังไม่มีจอ** (ปลายทางและ toast) |
| 2.2 | ตรวจสอบประวัติ | ยืนยัน | ไม่สำเร็จ | **ยังไม่มีจอ** |

**หน้าประวัติรอตรวจสอบ** (1 จอ)
- Filled มีประวัติรอตรวจสอบ (O.1)
- Default ไม่มีประวัติรอตรวจสอบ **ยังไม่มีจอ**

**หน้าตรวจสอบประวัติ** (4 จอ · หน้าเดียวกับประวัติงานบำรุงรักษาแบบดูอย่างเดียว + ปุ่มตีกลับและอนุมัติประวัติ)
- Default รอตรวจสอบ ปุ่มตีกลับและอนุมัติประวัติ (O.2)
- Interaction ตีกลับ popup ระบุเหตุผล (O.3)
- Confirm ยืนยันอนุมัติประวัติ "บันทึกเป็นประวัติทางการ" (O.4)
- Status อนุมัติแล้ว กล่องแจ้ง ปุ่มหาย (O.5) + toast H2
- Error Validation Field ไม่ระบุเหตุผลตีกลับ **ยังไม่มีจอ**

**Toast ของ J2**

| รหัส | ข้อความ | ชนิด | แสดงบนหน้า | เมื่อ | แทนจอเดิม |
|---|---|---|---|---|---|
| H2 | อนุมัติประวัติงานบำรุงรักษาสำเร็จ | Success | ตรวจสอบประวัติ | ยืนยันอนุมัติประวัติสำเร็จ | ชิ้นใน O.5 |
| | ตีกลับสำเร็จ (ร่าง รอข้อความจริง ไฟล์ 37) | Success | | **ยังไม่มีจอ** | |

### J3 ออกรายงานผลและปิดงาน

**ทางเดิน**

| # | อยู่หน้า | ทำอะไร | ผล | ไปหน้า |
|---|---|---|---|---|
| 1 | รายงานผลการบำรุงรักษา | ดาวน์โหลดรายงาน | | อยู่หน้าเดิม |
| 2 | รายงานผลการบำรุงรักษา | กดปิดงาน แล้วยืนยัน | สำเร็จ | อยู่หน้าเดิม สถานะปิดงานแล้ว + toast C1 |
| 2.1 | รายงานผลการบำรุงรักษา | ยืนยันปิดงาน | ไม่สำเร็จ | **ยังไม่มีจอ** |
| 3 | รายงานผลการบำรุงรักษา (ปิดงานแล้ว) | กดคำนวณต้นทุน | | ต้นทุนการบำรุงรักษา (J4) |

**หน้ารายงานผลการบำรุงรักษา** (3 จอ)

**Toast ของ J3**

### 4.2 การเรียงแบบตัว Z

```
ประวัติและปิดงาน                                ← Title หลัก 1 อัน
1 บันทึกและส่งประวัติ ───────────▶              1 journey = 1 แถวยาว
  1.1 หน้าประวัติงานบำรุงรักษา
2 ตรวจสอบประวัติ ─────────────▶
  2.1 หน้าประวัติรอตรวจสอบ │ 2.2 หน้าตรวจสอบประวัติ
3 ออกรายงานผลและปิดงาน · 4 คำนวณต้นทุน (แถวละ journey)
```

| ชั้น | หน้าตา | ตัวอย่าง |
|---|---|---|
| Title หลัก | component Header แบบ Type=Header (ไม่มี component ใช้กล่องสีเข้มแทน) · หัวส่วน Happy flow และทุกเคสใช้แบบเดียวกัน | ประวัติและปิดงาน |
| journey | แถบ Header แบบ Type=Subheader สถานะ Default กว้างทั้งแถว | 2 ตรวจสอบประวัติ |
| หน้า | แถบ Subheader สถานะ Sub Flow คร่อมจอของหน้านั้น | 2.2 หน้าตรวจสอบประวัติ |
| case | แถบ Subheader สถานะ Sub Flow 2 เหนือแต่ละจอ | 2.2.2 Interaction ตีกลับ ระบุเหตุผล (O.3) |
| ป้ายข้างแถว | component Device Type (Type = Header / Desktop / Mobile) ตามไฟล์ 32 หัวข้อ 4.2 | Device · Desktop · Mobile |

- สร้างบน Page "ประวัติและปิดงาน" กดแต่ละครั้งวางชุดใหม่ต่อใต้ของเดิม ไม่ลบไม่ย้ายของเดิม
- toast อยู่ในหน้าที่มันแสดง · Q.2 ไม่สร้าง (แทนด้วย toast Q1)

### 4.3 ปลั๊กอินที่สร้างตามหัวข้อนี้

ปลั๊กอิน `figma-export/maintainance-feature-plugin/` ใช้ฟังก์ชันวาดจอเดิมของ `maintainance-plugin/screens.js` ทุกจอ ต่างแค่การจัดวาง · ค่าของ Feature นี้อยู่ที่ `features/close.js`

FEATURE=close node figma-export/test-maintainance-feature-plugin.js                     # เทส ต้องได้คำเตือน 0

### 4.4 Happy flow

ทุกครั้งที่ export มีส่วน **Happy flow** ก่อนส่วนทุกเคส: เส้นทางหลักสั้นๆ ของแต่ละ journey แถวเดียว ป้ายเหนือจอ "ขั้น n · คำอธิบาย (รหัสจอ)"

| Journey | ขั้น |
|---|---|
| 1 บันทึกและส่งประวัติ | บำรุงรักษาครบทุกคัน (N.2) → ยืนยันส่งประวัติ (N.3) → ส่งแล้ว รอหัวหน้าตรวจสอบ (N.4) |
| 2 ตรวจสอบประวัติ | ประวัติรอตรวจสอบ (O.1) → ตรวจประวัติของแผน (O.2) → ยืนยันอนุมัติประวัติ (O.4) → อนุมัติประวัติสำเร็จ (O.5) |
| 3 ออกรายงานผลและปิดงาน | รายงานผลการบำรุงรักษา (P.1) → ยืนยันปิดงาน (P.2) → ปิดงานสำเร็จ (P.3) |
| 4 คำนวณต้นทุน | ต้นทุนการบำรุงรักษา (Q.1) → ดาวน์โหลด Excel สำเร็จ |

ขั้นสุดท้ายที่เป็นผลลัพธ์มี toast อยู่ในจอเลย (N.4 O.5 P.3 เป็นจอเดิมที่มี toast อยู่แล้ว · ขั้นสุดท้ายของ J4 คือหน้าต้นทุนที่มี toast ซ้อน `H:download`) ส่วนชุดทุกเคสใช้ toast แยกชิ้นตามหัวข้อ 0.2

## 5. ยังไม่มีจอ (ส่งให้เจ้าของงานตัดสิน)

1. ประวัติงานบำรุงรักษา: Status ถูกตีกลับ แสดงเหตุผลให้แก้แล้วส่งใหม่
2. ประวัติรอตรวจสอบ: ยังไม่มีประวัติรอตรวจสอบ
3. ตรวจสอบประวัติ: Error Validation Field ไม่ระบุเหตุผลตีกลับ
4. ตรวจสอบประวัติ: ปลายทางหลังตีกลับสำเร็จ และ toast ตีกลับสำเร็จ
5. toast ไม่สำเร็จ (general error) ของการส่งประวัติ อนุมัติหรือตีกลับ และปิดงาน
6. รายงานผลการบำรุงรักษา: หน้าตาไฟล์รายงานที่ดาวน์โหลด
7. ต้นทุนการบำรุงรักษา: ยังไม่มีข้อมูลต้นทุน (แผนยังไม่ปิดงาน)
