# พฤติกรรมร่วมของแจ้งซ่อม รับซ่อม และ Overhaul

ตรวจ UAT วันที่ 10 พฤศจิกายน 2569 ตามคำขอให้ behavior ของแต่ละงานสอดคล้องกัน. ใช้ร่วมกับ component library เดิมและ feedback ล่าสุดของแต่ละ flow.

## ขอบเขตที่ตรวจจากหน้าจอจริง

[รายการงานซ่อม](https://vms-plus-uat.odds.team/maintain-d/repair-utility-vehicle), [ฟอร์มแจ้งซ่อม](https://vms-plus-uat.odds.team/maintain-d/repair-utility-vehicle/new), รายละเอียดใบซ่อมฝั่ง กบค. ในสถานะรับเรื่อง/ตรวจสภาพก่อนซ่อม/รายงานปิดงาน, ขั้นนัดหมาย, แท็บข้อมูลและประวัติการดำเนินการ. เทียบกับ [Overhaul](https://vms-plus-uat.odds.team/maintain-d/overhaul-utility-vehicle) ที่ตรวจไว้ในรอบก่อน.

อ่านและเปลี่ยนเฉพาะ state ของฟอร์ม/ตัวกรองใน browser; ไม่มีการส่งใบแจ้งซ่อม เบิกอะไหล่ ลงนาม ส่งนัดหมาย หรือปิดงานจริง.

## การปรับที่ทำในปลั๊กอินรอบนี้

- `upload()` เปิดดาวน์โหลดไฟล์สำเร็จในหน้าดูอย่างเดียว คงห้ามลบ; ซ่อนดาวน์โหลดไฟล์ที่ยังอัปโหลด/ล้มเหลว และซ่อนกลุ่ม action เมื่อไม่มี action ที่ใช้ได้.
- `field()` เก็บค่าเลข 0 เป็น Filled ไม่สลับเป็น placeholder.
- `repairAppt()` ระบุเบอร์ติดต่อที่ระบบเติมเป็น Readonly; placeholder ค้นหาผู้ประสานงานของแบบสำรองใช้คำเดียวกับงานซ่อม.
- ฟอร์มสร้างแผนและสร้าง PO มี Back ซ้าย/Save ขวาเหมือนฟอร์มงานซ่อม; ฟอร์มแก้ไขคง Cancel/Save.
- state ออกจากฟอร์มสร้าง/แก้ไขแผนใช้ `EXIT_CONFIRM` เดียวกันและใช้ “ยกเลิก” สำหรับอยู่ต่อ.
- ข้อความชนิด/ขนาดไฟล์ของแผนและ PO ใช้ `DOC_HINT` เดียวกัน. Build SP09 ใหม่จาก source หลัก.

โค้ดปลั๊กอินสร้าง state ของแบบออกแบบ ไม่ใช่ browser application ที่เชื่อมข้อมูลจริง. การกรองแบบ draft/apply, dirty form, การทำรายการซ้ำระหว่างส่ง และสิทธิ์ backend ต้องตรวจตามกติกานี้เมื่อพัฒนา interaction; ไม่ถือว่าทดสอบจริงครบจากการเห็นเฟรมตัวอย่าง.

## ข้อกำหนดเฉพาะ flow ที่ต้องคงไว้

- แจ้งซ่อมมี 4 ขั้นในแบบฟอร์ม; งานรับซ่อมและ Overhaul มีขั้นปฏิบัติงานของตนเอง. ความสอดคล้องอยู่ที่ความหมายของ active/completed/back/submit ไม่ได้บังคับให้ใช้ชื่อหรือจำนวนขั้นเหมือนกัน.
- นัดหมายงานซ่อมที่ตรวจเป็นช่วงวันและเลือกเข้าซ่อมที่ กบค./ซ่อมหน้างาน. Overhaul ใช้อู่จาก PO และเงื่อนไขวัน/การข้ามขั้นที่ยืนยันแล้ว; ไม่เพิ่มตัวเลือกรูปแบบงานซ่อมเข้า Overhaul.
- ไม่เพิ่ม “ปิดงานทันที” ให้ Overhaul เพียงเพราะงานซ่อมมีปุ่มนี้. การข้ามขั้นและการอนุมัติใช้สิทธิ์/เงื่อนไขของ flow นั้น.
- ไม่ถ่ายทอดข้อบกพร่องของ UAT เป็นมาตรฐาน: เช่น จำนวนเงินเก่าที่ไม่มี .00, สถานะรับเรื่องกับขั้นที่แสดงไม่ตรงกัน หรือข้อความใน modal ที่ไม่ตรงงานที่ทำ ต้องแยกตรวจ ไม่ถือว่าเป็น requirement อัตโนมัติ.
- การส่งจริงและ toast หลังบันทึกไม่ได้ทดสอบบน UAT รอบนี้. คงข้อความที่ยืนยันแล้วจนกว่าจะมี feedback ใหม่; ไม่เปลี่ยน state diagram ของงานซ่อมหรือบทบาทผู้อนุมัติจากการดูหน้าจอ.

## Component และการตรวจ

ใช้ Text input, Input dropdown, File upload, Modal, Table header, Tabs, Progress steps, ReceiptChecklist และ HandoverSignature จาก (Component) VMS Plus; อ้างรูปแบบหน้าของ UI VMS Plus Release#2 ตาม component map เดิม. ไม่มี key หรือ component ใหม่.

`node figma-export/test-overhaul-shared-behavior.js` ตรวจการดาวน์โหลด/ลบตามสิทธิ์และสถานะอัปโหลด ค่า 0 เบอร์ Readonly คำแนะนำไฟล์ และข้อความยืนยันออก. รันร่วมกับ runtime callbacks ของ Overhaul และ SP09; ผล mock API ไม่ยืนยัน visual/import/font จริงใน Figma.
